# no-mistakes

**Кто:** Kun Chen (`kunchenguid`) — разбор автора в `[[tech/kun-chen-tdd-eval]]`.
**Статус:** записано для дела, **не устанавливалось**. Нужен отдельный старт от Романа.

## Суть

Слоган: **«Kill all the slop. Raise clean PR.»**

`no-mistakes` ставит **локальный git-прокси перед реальным remote**. Вместо
`git push origin` пишешь `git push no-mistakes` — он поднимает одноразовый
worktree, гоняет AI-валидационный пайплайн и форвардит ветку на реальный
push-target **только после того, как все проверки зелёные**, после чего сам
открывает чистый PR.

```
      твоя ветка
          │  git push no-mistakes
          ▼
 ┌────────────────────────────────────────────┐
 │ одноразовый worktree — твоя работа стоит  │
 │ review → test → docs → lint → push → PR → CI │
 └────────────────────────────────────────────┘
          │  всё зелёное
          ▼
      чистый PR, открыт за тебя
```

Ключевое свойство — **человек главный**: безопасные механические фиксы
применяются автоматически, всё, что **касается твоего интента**, эскалируется
тебе на approve / fix / skip. Это та же граница, что и в его тезисе про тесты:
агенту можно отдать исполнение, но не авторство требований.

## Три способа запуска (один и тот же пайплайн)

- **`git push no-mistakes`** — явный git-путь: пуш в gate-remote вместо `origin`
- **`no-mistakes`** — TUI; запускается после правок (коммит не нужен), мастер
  ведёт через ветку → коммит → push и цепляется за ран. `no-mistakes -y` всё
  делает автоматически
- **`/no-mistakes`** — скилл для агента: «сделай задачу и прогони через gate»
  или голый `/no-mistakes` для уже закоммиченной работы. `no-mistakes init`
  ставит скилл под Claude Code и других агентов

Внутри скилл ведёт `no-mistakes axi` — non-interactive TOON-интерфейс к тому же
approval-флоу. То есть проект опирается на экосистему AXI того же автора
(см. `[[tools/axi]]`).

## Пайплайн и поведение CI

- **Non-blocking:** гоняется в изолированном worktree, не рвёт твою работу
- **Agent-agnostic:** `claude`, `codex`, `grok`, `rovodev`, `opencode`, `pi`,
  `copilot`, `antigravity`, `cursor` / `devin` / `acp:<target>` через `acpx`,
  с упорядоченными фоллбэками; на каждом gate нужен запускаемый
  настроенный pipeline-агент
- **Чистый PR по умолчанию:** push → PR → смотрит CI → автофикс падений
- **Поведение при упавшем CI:** пайплайн чинит и публикует починку через тот же
  guarded force-push путь — но **только когда может доказать, что починка
  строится на том head, что ты уже просмотрел**. Не может доказать → починка
  идёт обратно через Review. Ремонт merge-конфликтов переписывает историю,
  поэтому всегда идёт по более безопасному пути. Флаг
  `ci.revalidate_repairs: true` — если каждую починку надо ревьюить (цена —
  полный повтор прогона)

## Риски и оговорки до установки

**1. `curl | sh` без проверки checksum.** Установка —
`curl -fsSL https://raw.githubusercontent.com/kunchenguid/no-mistakes/main/docs/install.sh | sh`.
Я прочитал скрипт (96 строк): он честный — качает архив с
`releases/download`, распаковывает в `mktemp -d`, `trap` чистит времёнку,
`sudo` используется **только** для создания симлинка в PATH. Но:

- **`checksums.txt` есть в релизе, а `install.sh` его НЕ проверяет** — архив
  скачивается и распаковывается вслепую
- **криптоподписи (cosign/minisign) у релизов нет** — сравнить не с чем. Для
  сравнения: у `destructive_command_guard` подписи minisign + cosign + sha256
  были (см. разбор dcg в сессии 08.10.2026)

Практически: скачивание по HTTPS с github.com приемлемо, но если ставить —
сверить `sha256sum` с `checksums.txt` вручную, это две строки.

**2. Hermes не в списке агентов.** Пайплайн-агенты: claude, codex, grok,
rovodev, opencode, pi, copilot, antigravity, cursor, devin, acp. **`hermes`
нет** — ни напрямую, ни в порядке фоллбэков. Теоретически подхватить можно
через `acp:<target>` через `acpx` (у нас Hermes v0.21.0, ACP-сокет надо
проверять отдельно), но это не штатный путь. Для Claude Code и OpenCode
работает из коробки.

**3. Инсталлятор ставит глобально.** `mv` бинаря в установочную директорию +
симлинк через `sudo ln -sf` — на нашем VPS это `/usr/local/bin`-подобный путь,
менять системный PATH-слой. Необратимо, но обратимо (`rm` симлинка).

**4. Нужен настроенный pipeline-агент.** «Every gate requires a runnable
configured pipeline agent» — то есть без установленного и настроенного
Claude Code/OpenCode/etc. пайплайн не запустится вообще. У нас из списка
доступен `opencode` (через opencode-go провайдер), остальное не установлено.

## Готовность VPS

- Go-бинарь, отдельного Node не требует (это про `axi`, там npm)
- Ассет `linux-amd64.tar.gz` есть — архитектура совпадает
- Для gate-режима нужен git-репозиторий с настроенным remote и агент из списка
- Влияние на существующее: **не работает как прокси, пока его явно не
  добавили как remote** — до `no-mistakes init` обычные `git push origin`
  не затрагиваются

## Как это соотносится с нашей работой

- Пайплайн `review → test → docs → lint → push → PR → CI` — это по сути то, что
  у нас лежит в `code-quality-workflow` (Section B: пре-коммит), но
  **встроено в git-путь** и с изолированным worktree
- Принцип «человек главный над интентом» совпадает с правкой
  `Boundary of the Iron Law` от 09.10.2026
- `[[tools/axi]]` внутри (через `no-mistakes axi` + TOON) — экосистема замкнута
- Наше правило про `git add -A` здесь не конфликтует — пайплайн сам решает,
  что коммитить, и в README `git add -A` не встречается

## Решение

**Не устанавливалось.** Зафиксировано для дела. Если будет ставить — вручную
сверить `sha256sum` бинаря с `checksums.txt`, и заранее понимать, что Hermes
в списке pipeline-агентов не значится (нужен acp-путь или Claude Code/OpenCode).
