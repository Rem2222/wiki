# Memory Wiki Workflow

Working with Rem's personal LLM-powered markdown wiki at `~/Documents/wiki/`.

## Wiki Structure

В вике два уровня каталогов. Короткие вики-ссылки идут в корневые каталоги, длинные — в `wiki/`.

```
~/Documents/wiki/          ← корень вики (vault root)
├── raw/                   — исходники (статьи, документы). Только чтение, не менять.
│
├── tech/                  — [[tech/name]] — технологии, инструменты, репозитории
├── tools/                 — [[tools/name]] — CLI-утилиты
├── projects/              — [[projects/name]] — проекты
├── events/                — [[events/name]] — события
├── videos/                — [[videos/name]] — видео
├── misc/                  — [[misc/name]] — всё остальное
├── articles/              — [[articles/name]] — статьи и разборы
├── books/                 — [[books/name]] — книги
├── concepts/              — [[concepts/name]] — концепции, идеи
│
├── wiki/
│   ├── tech/              — [[wiki/tech/name]] — SDD-инструменты, старые заметки, obsidian-экосистема
│   └── videos/            — [[wiki/videos/name]] — видео
│
├── index.md               — каталог всех страниц
├── log.md                 — журнал действий (append-only)
├── SCHEMA.md              — правила для LLM
└── AGENTS.md              — памятка для агентов
```

**Правило резолюции путей:** вики-ссылка `[[tech/name]]` → файл `/root/Documents/wiki/tech/name.md`. Ссылка `[[wiki/tech/name]]` → файл `/root/Documents/wiki/wiki/tech/name.md`. Если файла по одному пути нет, проверь другой — бывает дрейф путей (см. Pitfalls).

Подробный формат frontmatter — `references/wiki-frontmatter-standard.md`.

### Запись страниц — ТОЛЬКО через единый writer `wiki-write`

Все агенты (Hermes, Hermes Helper, Multica-автопилоты) пишут НОВЫЕ страницы в вики
через `/usr/local/bin/wiki-write` — единую точку записи, которая сама:
- генерит валидный YAML frontmatter (description/tags/related по стандарту ниже),
- пишет файл в нужную ветку (`tech/`, `tools/`, `concepts/`, ...) с латинизированным slug,
- `git add + commit + push origin master`,
- запускает фоновый rebuild zvec-индекса (не блокируя запись).

```bash
wiki-write --title "Название" --dir tech \
           --description "что это (2-3 предложения)" \
           --tags "a,b,c" \
           [--related "[[tech/x]] [[tools/y]]"] \
           --body /tmp/body.md          # файл с телом markdown
           [--update tech/existing.md]   # обновить существующую страницу
```

Правка существующей: `--update <relative-path>` — writer сохраняет связанные ссылки,
патчит frontmatter/тело, коммитит. НЕ редактируй .md напрямую без необходимости —
это ломает консистентность между разными агентами. Исключение: точечный фикс (опечатка,
одно поле) — можно через `patch`, но для новых/крупных страниц используй `wiki-write`.

`--no-push` / `--no-rebuild` — пропустить git-пуш или перестройку индекса.

## Page Format

Каждая страница — markdown с YAML frontmatter:

```markdown
---
description: Краткое описание (2-3 предложения, суть)
tags: [тег1, тег2]
related: [[Связанная страница1]] [[Связанная страница2]]
---

# Название

## Детали
...
```

**Поля frontmatter для content-страниц:**
- `description:` — обязателен. Одно предложение.
- `tags:` — массив lowercase-тегов. Хотя бы один.
- `related:` — `[[wikilinks]]` на связанные страницы. Если связей нет — можно убрать поле.

**⚠️ SCHEMA.md может быть устаревшим.** В SCHEMA.md указаны поля `title/type/created/updated/sources`, но реальные страницы вики используют `description/tags/related`. Опирайся на фактический формат существующих страниц, а не на SCHEMA.md.

## Rules

### Ingest (добавление одного источника)
1. Прочитать исходник
2. Создать/обновить страницу в соотв. категории
3. Расставить `[[wiki-links]]` на связанные страницы
4. Обновить `index.md` (добавить/обновить запись) — используй `patch`, НЕ `write_file`
5. Добавить запись в `log.md` — используй `patch` или `terminal("cat >> log.md")`, НЕ `write_file`
6. Обновить `related` на затронутых страницах

### Batch Ingest (множество источников за раз)

Когда Rem просит закинуть много ссылок в вику (3+):

1. **Параллельное исследование** — запусти `delegate_task` с батчами по 3 task'а. Каждый исследователь **только собирает информацию** (README, сайт, описание) и возвращает структурированный обзор. **Исследователи НЕ создают файлы** — всю запись в вики делает основной агент после получения всех обзоров. В контекст каждой задачи передавай полный абсолютный путь к будущему файлу (`/root/Documents/wiki/PATH/имя.md` — PATH уточни по префиксу вики-ссылки) для однозначности.
2. **Дождись всех результатов** — все батчи должны завершиться.
3. **Создай все страницы сразу** — одной серией `write_file` (новые страницы, не перезаписывающие существующие). Поле `source:` в frontmatter = URL источника.
4. **Обнови `index.md`** — добавь все записи в соответствующие секции через `patch`.
5. **Обнови `log.md`** — одной записью вида `## [дата] ingest | N источников (батч)` со списком вложенных страниц. Используй `patch` (добавить в конец), НЕ `write_file`.
6. **Обнови дату** в заголовке `index.md` (`_Обновлено: YYYY-MM-DD_`).
7. **Запушь в гит:**
   ```bash
   cd ~/Documents/wiki && git add . && git commit -m "wiki: +N страниц: тема1, тема2..." && git push
   ```

**Категоризация страниц:**
- `tech/` — технологии, инструменты, сервисы, GitHub-репозитории (кроме CLI-утилит)
- `tools/` — CLI-утилиты, консольные инструменты, мета-скиллы
- `events/` — новости, анонсы, твиты, конференции
- `concepts/` — абстрактные концепции и идеи
- `projects/` — собственные проекты Rem
- `articles/` — статьи и разборы
- `videos/` — видео-контент

**Формат ссылок в index.md:**
- Секция `## Технологии`: `[[tech/name]]`
- Секция `## Концепции`: `[[concepts/name]]`
- Секция `## События`: `[[events/name]]`
- Секция `## Инструменты`: `[[tools/name]]`
- Секция `## Видео`: `[[videos/name]]`
- Секция `## Проекты`: `[[projects/name]]`
- Секция `## Статьи`: `[[articles/name]]`
- Секция `## SDD-инструменты (детали)`: `[[tech/name]]`
- Секция `## Obsidian & экосистема`: `[[wiki/tech/name]]` (исторически, файлы лежат в wiki/tech/)
- Секция `## Прокси и инфраструктура`: `[[wiki/tech/name]]`
- Секция `## Книги`: `[[books/name]]`
- Секция `## Разное`: `[[misc/name]]`

### Query (ответ на вопрос)
1. **Сначала zvec** — гибридный семантический поиск по Markdown-вики (`~/Documents/wiki/`). Два интерфейса:
   - **MCP-tool `zvec_wiki_search(query, topk, page_only)`** — нативный инструмент Hermes (рекомендуется, если доступен в сессии). Возвращает JSON `[{page, category, title, score, snippet}]`.
   - CLI `zvec-wiki "<query>"` — то же через shell. `--page-only` — краткий список страниц, `--json` — машинный вывод.
   Индекс на zvec (вектор bge-m3 + FTS, RRF) — ищет и по смыслу, и по ключевым словам.
2. **Потом index.md** — если zvec не дал результата, прочитай `index.md` для поиска по категориям
3. **Прочитать нужные страницы** — `read_file` из `~/Documents/wiki/`
4. **Синтезировать ответ**
5. Если ответ ценный — сохранить как новую страницу (в локальную вику; GBrain остаётся как бэкап до cutover)

**Почему zvec первым:** zvec покрывает все Markdown-файлы вики с полным текстом (FTS) + векторными эмбеддингами (bge-m3). `index.md` — это ручной каталог, который может устаревать. zvec находит даже то, что не было явно залинковано в index.md.

### Nightly Health Check (быстрая проверка здоровья)

Запускается каждую ночь в рамках автопилота «Ночная рутина» (Step 10). Флажит проблемы без исправления. Порог создания подзадачи на аудит — >10 проблем.

```bash
python3 /root/.hermes/scripts/wiki-health-check.py
```

Проверяет: frontmatter, description/tags/related, множественные H1, битые [[wikilinks]], страницы-сироты, git conflicts.

Если проблем > 10 — агент создаёт подзадачу на полный Maintenance Audit (см. ниже).

После масс-фикса (100+ страниц) — обязательно `git pull --rebase` перед `git push`, иначе Obsidian Git plugin создаст конфликт на телефоне Rem.

### Maintenance Audit (полная проверка здоровья вики)

Когда Rem просит «приберись в вики» / «проверь вики» / «сделай обслуживание» или когда ночной чек показал >10 проблем:

1. **Бэкап** — `git commit` + `tar czf`
2. **Инвентаризация** — список всех .md файлов по категориям
3. **Frontmatter check** — какие страницы без frontmatter
4. **Header lint** — множественные H1, старый формат метаданных
5. **Поиск битых вики-ссылок** — `[[target]]` которые не ведут ни на один существующий файл
6. **Поиск `wiki/` префикс-дрейфа** — ссылки вида `[[wiki/concepts/X]]` когда файл лежит в `concepts/X.md`
7. **Создание недостающих страниц** — для важных концепций, на которые много ссылок
8. **Фикс найденных проблем**
9. **Обновление index.md** — если добавлялись/удалялись страницы
10. **git commit**

Подробные команды для каждого шага — в `references/wiki-audit-procedure.md`.
Стандарт frontmatter — в `references/wiki-frontmatter-standard.md`.
Масс-фикс 100+ страниц — в `references/wiki-mass-fix-patterns.md`.

### Important
- **Не галлюцинировать** — если не уверен, спросить Rem
- **Ссылки > дублирование** — лучше `[[link]]` чем копировать текст
- **Обновлять updated** — при любом изменении страницы
- **Не трогать `raw/`** — это read-only источники
- **`log.md` append-only** — только добавлять записи

## GBrain Wiki Workflow (альтернативный путь)

У Rem теперь **два места** для вики-страниц:

1. **Локальная файловая система:** `~/Documents/wiki/` — описана выше. Синхронизируется с Obsidian через CouchDB/LiveSync.
2. **GBrain (MCP):** через `mcp_gbrain_put_page` — живёт в векторной БД. Доступна через GBrain search/query.

### Когда что использовать

| Сценарий | Куда писать |
|---|---|
| Заметка для Obsidian, файл нужен в редакторе | Локальная вика (`~/Documents/wiki/`) |
| Краткий обзор инструмента/проекта для быстрого поиска | Локальная вика (+ zvec-wiki её индексирует) |
| Нужна интеграция с вики-ссылками `[[wikilinks]]` | Локальная вика |
| Нужен full-text/семантический поиск | **zvec-wiki** (гибрид вектор bge-m3 + FTS по `~/Documents/wiki/`) |
| Пользователь сказал «в вики» — и не уточнил | Уточни: локальная вика или GBrain |

> **Семантический поиск теперь на zvec.** GBrain (MCP) остаётся как бэкап до подтверждённого cutover (MUL-878): его НЕ удалять, в него по-прежнему можно писать `mcp_gbrain_put_page`, но читать/искать вики семантически нужно через `zvec-wiki`.

### GBrain put_page формат

Формат страницы — markdown с YAML frontmatter, как и в локальной вике, но с дополнительным source-контекстом:

```markdown
---
description: Краткое описание
tags: [тег1, тег2]
related: [[related-page]]
---

# Заголовок

## Что это

## Детали
```

**Особенности:**
- Slug выбирается по структуре: `tools/name`, `tech/name`, `projects/name` и т.д.
- Tags и description обязательны — из них GBrain строит поисковые индексы
- GBrain сам парсит `[[wikilinks]]` из контента в граф связей (но только при включённом auto_link — на удалённом вызове может быть `skipped: "remote"`, как в этой сессии)
- `mcp_gbrain_put_page` создаёт или обновляет страницу по slug
- Для большого контента (свыше ~45KB) используй `gbrain capture --file PATH --slug SLUG` из terminal

### Сопоставление slug-префиксов с категориями

| Категория | GBrain slug-prefix | Локальная вика |
|---|---|---|
| Технологии | `tech/` | `~/Documents/wiki/tech/` |
| Инструменты | `tools/` | `~/Documents/wiki/tools/` |
| Проекты | `projects/` | `~/Documents/wiki/projects/` |
| События | `events/` | `~/Documents/wiki/events/` |
| Концепции | `concepts/` | `~/Documents/wiki/concepts/` |
| Статьи | `articles/` | `~/Documents/wiki/articles/` |

Старайся сохранять единый slug-префикс в GBrain для согласованности с локальной викой.
- **⚠️ Инфраструктура в вики может быть устаревшей.** Вики содержит записи со старого VPS (81.17.100.103 / rem2222.top) — CouchDB, Obsidian LiveSync, Authelia, сервисы — данные которого утеряны. Опираться только на то, что делали вместе на текущем сервере (80.241.218.110). Не ссылаться на сервисы из старых страниц как на рабочие, если не проверено.
- **🚫 НИКОГДА не перезагружать сервер, Hermes Agent, gateway или другие тулзы без явного разрешения Rem.** На сервере могут работать несколько агентов — перезагрузка нарушит их работу.
- **🔍 Когда Rem просит «поищи в памяти» / «вспомни» / «что там по …» — используй ВСЕ доступные источники памяти:** session_search (прошлые сессии), wiki (база знаний), agentmemory (MCP), GBrain (MCP), любой другой подключённый memory MCP. Не ограничивайся одним источником. Загрузи соответствующие скиллы, если нужно.

### Pitfalls

⚠️ **Не используй `write_file` на `log.md` или `index.md`.** Они перезаписываются целиком. Для `index.md` используй `patch` (добавить строку в секцию). Для `log.md` — `terminal("echo ... >> log.md")`.

⚠️ **Сабагенты пишут файлы в неправильные пути.** При batch ingest через `delegate_task` передавай полный абсолютный путь в контексте каждой задачи. После завершения проверь результат.

⚠️ **Имена файлов не должны содержать пробелов.** Файл `Mercury Agent Skills.md` пришлось переименовать в `Mercury-Agent-Skills.md`, потому что пробелы ломают вики-ссылки и grep-поиск. Используй дефисы.

⚠️ **Проверяй git state перед любой работой.** Если в `.git/` есть `MERGE_MSG` или `REBASE_HEAD` — сначала заверши/отмени операцию. Иначе твои изменения попадут в конфликт с Obsidian Git plugin на телефоне Rem. См. `references/wiki-audit-procedure.md` шаг 0.

⚠️ **После коммита предупреди Rem о возможном Git конфликте в Obsidian.** Obsidian Git plugin делает авто `git pull --rebase` при синке. Если за время работы на сервере появились новые коммиты — пользователь увидит диалог конфликта на мобилке.
- **При масс-фиксе (100+ страниц):** после `git commit` делай `git pull --rebase origin master` перед `git push`. Obsidian Git plugin мог записать коммиты за время твоей работы.

⚠️ **Дубликаты `tags:` в frontmatter.** При конвертации старых страниц (# title + **Field:** метаданные → YAML ---) может остаться пустое `tags:` в теле frontmatter после уже добавленного `tags: [tech]`. Проявляется как 2 строки `tags:` — одна с содержимым, вторая пустая. После механического фикса запусти проверку: если grep находит 2+ `tags:` в одном файле — удали лишнюю.

⚠️ **SCHEMA.md может быть устаревшим.** Реальный frontmatter-формат страниц — `description/tags/related`, а не `title/type/created/updated/sources` как написано в SCHEMA.md. При создании новых страниц ориентируйся на существующие примеры.

⚠️ **Не все `[[wiki/...]]` ссылки — битые.** У вики два уровня каталогов. `[[wiki/tech/name]]` — валидная ссылка на файл в `wiki/tech/name.md`, если такой существует. `[[wiki/concepts/sdd]]` — битая, если файл лежит в `concepts/sdd.md`. Проверяй оба пути.

⚠️ **Масс-фикс битых `[[bare-name]]` ссылок.** Многие старые страницы ссылаются на `[[mcp]]` вместо `[[concepts/mcp]]` или `[[multica]]` вместо `[[tech/multica]]`. Исправлять надо через resolution map:
  1. Собери все bare-name target'ы (без `/` в имени)
  2. Для каждого проверь все категорийные префиксы (`tech/`, `concepts/`, `tools/`, `events/`…)
  3. Замени `[[bare]]` → `[[tech/bare]]` в исходных файлах
  См. `references/wiki-mass-fix-patterns.md` → раздел «Bare wikilink resolution».

⚠️ **Не создавай `[[status.*]]` как вики-ссылки.** Если страница содержит `[[status.ready]]`, `[[status.todo]]`, `[[status.toread]]` — это не страницы, а маркеры статуса. Заменяй на `status: ready` / `status: todo` / `status: toread` в тексте.

⚠️ **Порядок масс-фикса имеет значение.** При аудите 100+ страниц соблюдай порядок:
  1. Frontmatter (--- YAML)
  2. Descriptions (авто-генерация из первого параграфа)
  3. Tags (по категории директории)
  4. Multi-H1 (демотить # → ##)
  5. Broken wikilinks (сначала resolution map, потом стабы)
  6. `git pull --rebase` → commit → push
  Нарушение порядка = дублирующаяся работа (фикс H1 в странице без frontmatter придётся делать заново).

### Recovery (если `log.md` случайно перезаписан)

Вика — git-репозиторий (`~/Documents/wiki/.git/`). Восстановить `log.md`:

```bash
cd ~/Documents/wiki && git show HEAD:log.md > log.md
```

Затем повторно добавить запись (через `patch`, не `write_file`).

## Research Protocol (поиск решений для Rem)

Когда Rem просит найти/сравнить инструменты или решения:

1. **Сначала проверь вики через zvec.** Используй `zvec-wiki "<query>"` для гибридного семантического поиска по Markdown-вики — он находит даже то, что не залинковано в index.md. Если zvec вернул релевантные страницы — читай их. Если нет — открывай `index.md` и ищи по категориям.

2. **Потом ищи снаружи.** Только после того, как выяснил что уже есть в вики — дополняй внешними источниками (GitHub, HN, Reddit).

3. **Сравнивай с тем что есть в вики.** Явно покажи, как новое соотносится с уже известными Rem решениями — что дополняет, что заменяет, что устарело.

4. **Фишка каждого решения.** При сравнении всегда выделяй уникальную особенность — чем этот вариант отличается от остальных, в чём его главная идея (например: "единственный с доказанной экономией токенов", "спроектирован специально под твой стек", "самоорганизующаяся — сама решает что забыть"). Без этого сравнение выглядит плоским списком.

5. **"Зачем мне это?" (practical relevance filter).** Когда Rem спрашивает про конкретный инструмент и оценивает его применимость — отвечай не только "что это", но и "зачем это тебе / не тебе". Явно разбери:
   - **Нужно ли это Rem?** (совместимость со стеком, реальная польза, альтернативы которые уже есть)
   - **Работает само или требует ручного труда?** (autonomous vs manual setup)
   - **Готово к production или research?** (стадия зрелости)
   - **Что можно взять** из проекта, даже если сам инструмент не ставить (идеи, архитектура, концепты)

6. **Формат сравнения.** Давай не просто таблицу, а:
   - Фишка (одной строкой)
   - ✅ Плюсы (коротко, по делу)
   - ❌ Минусы (честно)
   - Для топ-вариантов — развёрнутое "почему именно это" под каждый сценарий Rem

### Known preferences for Rem comparisons
- Язык: русский
- Стиль: структурированно, маркированные списки, без воды

- Говори на том же языке, на котором Rem к тебе обратился

### Research → Wiki → Action Pipeline (deep-dive из репозитория или статьи)

Когда Rem просит исследовать GitHub-репозиторий, Habr-статью или другой источник, а потом углубляется в конкретные темы (RAG, MCP, DPI, архитектура и т.д.):

1. Сделай быстрый обзор (Phase 1 в `references/repo-deep-dive-workflow.md`)
2. Запусти параллельное исследование через `delegate_task` (Phase 2)
3. Если Rem спрашивает про практическое использование в коде — SDK deep-dive (Phase 2.5)
4. Сохрани результаты в вику — отдельную страницу на каждую тему, при multi-source синтезе объединяй в одну связную страницу (Phase 3)
5. Создай action в agentmemory на изучение (Phase 4)
6. Если нужен follow-up — one-shot cron на проверку (Phase 4b)
7. Сохрани lesson (Phase 5)

Подробный pipeline с примерами и pitfalls — в `references/repo-deep-dive-workflow.md`.
