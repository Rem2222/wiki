# Выбор LLM для этапов разработки

## Проблема: миф «стратегия требует умнейшей LLM»

Вендоры (и часть сообщества) продвигают идею, что для архитектурного проектирования нужна самая дорогая модель (Opus, Pro, Ultra). Это выгодно вендорам, но не соответствует реальности.

## JPEG-аналогия

Разница между LLM одного семейства (Flash vs Pro, Sonnet vs Opus) ≈ разница между JPEG-изображениями с разной степенью сжатия:

- **Маленькая модель (SLM)** — JPEG с сильным сжатием. Силуэт (архитектура, паттерн, best practice) сохраняется чётко, но мелкие детали (конкретные API, редкие вызовы) размыты.
- **Большая модель (LLM)** — JPEG с низким сжатием. Те же силуэты + оригинальные «перья» (детали).

При инференсе маленькая модель **достраивает** утраченные детали из вероятности — может придумать несуществующий API, который выглядит правдоподобно. Большая вспомнит оригинал.

## Что одинаково

Для **стандартных архитектур** (CRUD, REST API, микросервисы, event-driven) — большая и маленькая модель увидят один и тот же «силуэт». DeepSeek Flash спроектирует архитектуру не хуже DeepSeek Pro, потому что паттерны одинаково сохранены в весах обоих.

## Что различается на самом деле

| Аспект | Маленькая модель | Большая модель |
|--------|-----------------|----------------|
| **Знание best practices** | ✅ одинаково | ✅ одинаково |
| **Знание редких API/фреймворков** | ⚠️ галлюцинирует | ✅ вспоминает |
| **Детали UI/стилей** | ⚠️ размыто | ✅ чётко |
| **Глубина рассуждения** | ❌ поверхностно | ✅ многопланово |
| **Перебор альтернатив** | 2-3 варианта | 5-10 вариантов |
| **Дальновидение (anticipating edge cases)** | ⚠️ базово | ✅ глубоко |

## Ключевое уточнение к JPEG-аналогии

JPEG описывает **статическое знание** (детали), но не описывает **динамику рассуждения** (reasoning depth). Большая модель может:

1. Потратить больше thinking tokens на исследование дерева решений
2. Заметить противоречия между требованиями на 5 шагов глубже
3. Увидеть, что выбранный паттерн сломается при масштабировании

Это не «знание деталей» — это **capacity рассуждения**. SLM с 4B не хватит «вычислительного пространства» для длинной цепочки reasoning.

## Оптимальная стратегия

| Этап | Какая модель | Почему |
|------|-------------|--------|
| **1. Архитектура / Brainstorm** | Reasoning-модель (o1, DeepSeek R1) | Нужен перебор альтернатив, а не знание API |
| **2. Спецификация / требования** | Flash / Sonnet / средний уровень | Уже ясно что делать, нужна скорость |
| **3. Первая генерация кода** | Pro / Opus / старшая модель | Детали API без галлюцинаций, правильный «первый проход» |
| **4. Итерации / отладка** | Flash / Sonnet / младшая модель | Код уже есть — few-shot сработает, знание деталей подтягивается из контекста |

## Заблуждения

1. ❌ «Архитектуру должен делать самый умный» — для 80% проектов любой Flash нарисует тот же силуэт
2. ❌ «Opus бесполезен как кодер» — наоборот, его сила в деталях, а не в стратегии
3. ❌ «Большая модель всегда дороже для всего» — если разбить правильно, большую модель используют только на 20% задач, а 80% идут на Flash/Sonnet

## Применение к GSD-агентам (Hermes Agent / Multica)

Текущая конфигурация использует DeepSeek V4 Flash для всех агентов (через OpenCode Go). Согласно стратегии, стоит перераспределить:

| Агент GSD | Роль | Сейчас | Нужно | Почему |
|-----------|------|--------|-------|--------|
| **Executor** | Пишет код | Flash | **Pro** | Первая генерация — нужны детали API без галлюцинаций. Flash «придумает перья», Pro вспомнит |
| **Planner** | Архитектура | Flash | **R1 / reasoning** | Нужна глубина рассуждения, перебор альтернатив. Flash знает «силуэт», но не увидит проблему на 5 шагов вперёд |
| **Code Reviewer** | Ревью кода | Flash | **Pro** | Детали безопасности и редкие баги |
| **Security Auditor** | Аудит | Flash | **Pro** | Критично знать точные детали CVE, паттернов уязвимостей |
| **Debugger** (сложный) | Дебаг | Flash | **Pro/Flash** | Если баг в редком фреймворке — Pro; если типовой — Flash |
| **Researchers** | Исследование | Flash | **Flash** ✅ | «Силуэт» информации — Flash видит не хуже |
| **Plan Checker** | Проверка плана | Flash | **Flash** ✅ | Паттерны стандартные |
| **Verifier** | Верификация | Flash | **Flash** ✅ | Достаточно «силуэта» |

### Доступные провайдеры

- `opencode-go/deepseek-v4-flash` — **младшая** (80% задач)
- `opencode-go/deepseek-v4-pro` — **старшая** (генерация кода, ревью)
- `alibaba-tp/deepseek-v4-pro` — запасная старшая
- `alibaba-tp/qwen3.7-max` — альтернатива Pro
- DeepSeek R1 — если появится в OpenCode Go или через Alibaba TP

### Ключевой вывод

Не использовать Pro для архитектуры только потому что «она умнее». Pro нужна там, где критичны **детали** (первая генерация кода, ревью безопасности). Для архитектуры и стратегии важнее **reasoning capacity** — тут нужна R1/o1, а не просто большая модель.
