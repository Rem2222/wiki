# LLM-as-a-Verifier

Фреймворк для **верификации** ответов/решений LLM (не для генерации). Считает, насколько один результат лучше другого, используя не текст, а **вероятностные распределения** токенов-оценок (logprobs). Идея-усилитель для крупных и сложных задач, где дешёвая проверка «на глаз» ненадёжна.

- **GitHub:** https://github.com/llm-as-a-verifier/llm-as-a-verifier
- **Установка:** `pip install llm-verifier` (Python, v0.2.0 на 20.08.2026)
- **Лицензия / статус:** open-source

## Зачем это нужно

Когда задача большая или сложная, одиночный ответ LLM может быть «удачным случайно». Хочется:
- прогнать N вариантов (доработок, решений) и выбрать лучший — **Best-of-N**;
- **самоверифицировать** результат той же моделью (self-verification) на сложном бенчмарке;
- получить **плавную шкалу качества 0..1** вместо «ок/не ок».

## Три ключевые идеи

1. **Мелкозернистая шкала.** Вместо «правильно/неправильно» — числовая оценка 0..1 (напр. `0.87`), что позволяет ранжировать и сравнивать близкие кандидатов.
2. **Математическое ожидание по распределению logprob.** Модель генерирует токен-оценку (например букву шкалы). Вместо одного сэмпла берётся распределение вероятностей по кандидатам и считается `score = Σ P(token)×значение(token)` — усреднение, устойчивое к шуму отдельного сэмпла.
3. **Повторные оценки + декомпозиция.** `n_evaluations` прогонов, критерии раскладываются на под-критерии; + Pivot-турнир O(Nk) вместо попарного O(N²) при выборе из N кандидатов.

## API (v0.2.0)

- `select(problem, candidates, criteria, ...)` → **Best-of-N** (`VerifierResult` с рейтингом кандидатов);
- `compare(problem, trace_a, trace_b, criteria, ...)` → попарная награда `(score_a, score_b)`;
- `track(problem, steps, checkpoint_steps, ...)` → пошаговый прогресс с чекпоинтами.

Опции: `n_evaluations` (сколько прогонов), `pivots` (турнир), `model`, `client`, `cache`/`progress`.

## Бенчмарк Terminal-Bench 2.1 (self-verification)

Улучшение при самоверификации (та же модель себя верифицирует, 5 траекторий на задачу):

| Режим | Без верификатора | С верификатором | Oracle |
|---|---|---|---|
| Best-of-3 | 79.4% | **86.5% ± 1.1%** | 92.1% |
| Best-of-5 | 78.7% | **88.0% ± 0.6%** | 96.6% |

Также в v0.2.0: prefix-cache (~3.4× меньше некэшированных токенов), token accounting (`llm_verifier.token_usage()`).

## Ключевое требование: top-k logprobs

Чтобы считать распределение, сервер должен отдавать **не только выбранный токен, но и альтернативы с вероятностями** (`top_logprobs`/`top-k`).

В коде фреймворка (fine_grained_reward.py): на каждый токен берётся `pos.top_logprobs`; если списка нет — подставляется один токен, и оценка **вырождается в ничью 0.5/0.5** (теряется вся польза).

Серверы, которые это умеют (по докам фреймворка): **vLLM, SGLang, OpenAI API, DeepSeek API**. Фреймворк заявлен нативно под `DEEPSEEK_API_KEY` + `deepseek-v4-flash` как verifier-backend.

## Проверка на текущем стеке (20.08.2026)

Проверено вживую на `opencode-go` (`opencode.ai/zen/go/v1`, модель `deepseek-v4-flash`):

| Возможность | opencode-go |
|---|---|
| принимает `logprobs: true` | ✅ |
| отдаёт `logprob` выбранного токена | ✅ (`{token, logprob, bytes}`) |
| отдаёт `top_logprobs` (альтернативы) | ❌ поле отсутствует даже при `top_logprobs:3` |

Прогон `llm_verifier` через opencode-go:
- `compare` → `(0.5, 0.5)` — не различает кандидатов;
- `select` → index правильный, но **случайно** (модель «в прозе» склоняется к верному), все `scores: [0.5,0.5,0.5]`.

**Вывод по стеку:** opencode-go не отдаёт топ-k logprobs → фреймворк деградирует до слепого режима. Локальные модели (Ollama qwen2.5:7b и т.п.) — слабые и не отдают топ-k. Реально работает только на **официальном DeepSeek API** (или vLLM/SGLang с приличной моделью).

## Итог и рекомендация

**Статус для текущего стека: НЕ применимо сейчас** (нет ни топ-k logprobs у провайдера, ни достаточно сильной локальной модели). Это **перспективный усилитель LLM** на больших и сложных задачах (крупные доработки 1С, выбор среди многих вариантов, сложные интеграции), к которому стоит вернуться при появлении:
- официального `DEEPSEEK_API_KEY`, или
- достаточно сильной локальной модели под vLLM/SGLang с топ-k.

Тогда `select` (Best-of-N) — прямой fit для автономной разработки, где важно выбрать лучшую из нескольких доработок (см. [[articles/1c-autonomous-ai-development]]).
