# NVIDIA Auto Ontology

Открытая библиотека NVIDIA для построения **семантического слоя** над данными: собирает онтологию из метаданных предприятия, сводит расходящиеся определения между системами и отдаёт результат любому агенту через **MCP, CLI и API**. Ключевая идея — агент получает не список таблиц, а подтверждённые определения, связи и наследуемость, и сгенерированный SQL проверяется по этим определениям.

## Факты по репозиторию (проверено 2026-10-28)

- `NVIDIA/auto-ontology`: **481 ⭐**, 61 форк, Apache-2.0
- Языки: Python (основной), TypeScript, PLpgSQL
- Создан 2026-04-27, последний push 2026-10-28, 27 открытых issues — живой, но молодой проект
- Репозиторий замеров из поста: `NVIDIA/ontology-sql-eval` отдаёт **301** и переехал в **`auto-ontology-eval`** (10 ⭐, 3 форка, Apache-2.0, создан 2026-07-02). Описание: набор для оценки text-to-SQL — загрузка схемы, оценка retrieval, отдельный SQL-судья и пересчёт скоринга
- **Внешние пул-реквесты не принимаются** — это прямо в README; доработки только своим форком

## Возможности (по README)

Пять ролей, которые библиотека берёт на себя:

- **Discover** — генерировать онтологии из метаданных, подключать существующие онтологии и семантические модели, строить граф знаний, готовый для ИИ
- **Ground** — давать агенту доверенный бизнес-смысл метрик, сущностей и связей; сводить несогласованные определения между системами
- **Validate** — проверять сгенерированные запросы по сертифицированным определениям и lineage, возвращать происхождение вместе с ответом
- **Expose** — отдавать контекст любому агенту через MCP, CLI или API
- **Learn** — складывать подтверждённые исправления и историю использования обратно в онтологию, чтобы контекст уточнялся с каждым вопросом

Источники данных: **Postgres, Snowflake, Databricks, DuckDB**.

## Устройство стека

- Frontend: Next.js 16 (React 19, TypeScript, Tailwind 4), Better Auth, Prisma — веб-интерфейс, аутентификация, API-шлюз (порт 3000)
- Backend: FastAPI (Python 3.12+), LangChain — чат, NL-to-SQL, каталог, API к источникам (3001)
- Ingestion worker: FastAPI — загрузка табличных данных и запись эмбеддингов (3002)
- **Postgres + pgvector** — метаданные приложения, каталог, онтология и векторное хранилище (5432)
- HashiCorp Vault — опционально

Развёртывание: Helm-чарт для Kubernetes или Docker Compose для локального стека; в стеке есть pgAdmin.

Инференс по умолчанию — **NVIDIA NIM** (нужен ключ `nvapi-...`):

- LLM: `nvidia/nemotron-3-nano-30b-a3b`
- Эмбеддинги: `nvidia/nemotron-3-embed-1b`
- Переранжирование: `nvidia/llama-nemotron-rerank-vl-1b-v2`

Слой MCP: отдельный сервер в каталоге `mcp/`, документация — `docs/mcp.md`.

## Оговорки, которых нет в промо-описаниях

- **Креды подключения к источникам по умолчанию лежат в Postgres в открытом виде** — в README это оговорено отдельно; есть вариант с Vault. Для пароля к рабочей базе это существенный риск
- Нужен внешний ключ NVIDIA NIM, то есть инференс не бесплатный и не локальный по умолчанию
- Стек тяжёлый: Postgres с pgvector, Next.js, FastAPI, отдельный worker, pgAdmin — не «одна кнопка» на слабой машине
- Проект молодой (создан в апреле 2026), внешние исправления не принимаются — рассчитывать на скорость правок под свой случай не стоит

## Как применить к PostgreSQL с 1С

Задача-пример: дать агенту возможность напрямую формировать запросы к базе 1С, живущей в PostgreSQL. Подробности доступа к самой базе — в заметке [[tech/1c-postgres-readonly]], здесь — про слой смысла.

**В чём подвох 1С.** Метаданные в базе 1С — это сгенерированные платформой имена: `_ReferenceNN`, `_DocumentNN`, `_FldNNNN`, а ссылки на объекты лежат в двоичном виде в `_IDRRef` (16 байт). Смысла в этих именах нет, и онтология, построенная «как есть», будет столь же бессмысленной: агент уверенно построит запрос к `_Reference123`, не зная, что это «Номенклатура». Имена меняются при изменении конфигурации и реструктуризации.

**Откуда взять смысл.** В контуре на 141-й машине уже подняты MCP-серверы метаданных 1С: `1c-code-metadata-mcp` (28 инструментов) и `1c-graph-metadata-mcp` (55). Они знают соответствие «таблица в PostgreSQL ↔ объект метаданных 1С ↔ реквизиты ↔ связи». Именно они — правильный источник наполнения онтологии.

**Рабочая схема:**

1. Выгрузить соответствия из `1c-code-metadata-mcp` / `1c-graph-metadata-mcp` (объекты, реквизиты, таблицы, связи).
2. Загрузить их в онтологию (у Auto Ontology — через ingestion/каталог, в простом варианте — своей таблицей в Postgres с pgvector).
3. Подключить источник PostgreSQL **только на чтение** (отдельная роль, `GRANT SELECT`, `default_transaction_read_only=on`, `statement_timeout`, `LIMIT`), желательно на копии базы или реплике, а не на рабочей.
4. Отдать агенту через MCP: сначала метаданные и определения, потом SQL с проверкой по онтологии и возвратом lineage.

**Практический совет по порядку действий.** Начинать с дешёвого прототипа, а не с разворачивания всего фреймворка: таблица-онтология в Postgres с pgvector («таблица ↔ объект метаданных ↔ поля ↔ связи»), наполняемая скриптом из `1c-metadata` MCP — это порядка двухсот строк кода и даёт основную пользу без ключа NIM и без чужого стека. Auto Ontology примерять вторым шагом — ради готового UI, каталога, RBAC и валидации запросов, если прототип себя оправдает.

**Ресурсы.** Для нашего VPS (11 ГБ RAM, около 26 ГБ свободного диска) стек тесноват, но подъёмный; комфортнее — на XE2690 или на 141-й машине рядом с 1c-metadata серверами.

**Чего делать нельзя.** Писать в базу 1С напрямую: `INSERT`/`UPDATE` в обход платформы ломает регистры и версии объектов, то есть портит учёт без возможности восстановить логикой. Только чтение.
