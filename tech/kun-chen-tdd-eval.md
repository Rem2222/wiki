## 3. Мой расчёт мощности (это не считал автор)

Числа: 145/222 против 147/222.

- Разница — **ровно 2 прогона** из 222
- z ≈ 0.200, **p ≈ 0.841**
- 95% доверительный интервал разницы: **[−7.9 п.п., +9.7 п.п.]**
- При 80% мощности минимальный детектируемый эффект — **12.6 п.п.**
- Чтобы поймать эффект в 5 п.п., нужно **~1 413 прогонов на руку** (сейчас 222)
- Для 10 п.п. — **~354 на руку**

**Важно про 444 прогона:** это 111 задач × 2 руки × 2 повтора. Уникальных задач
**111**, повторы внутри задачи коррелированы — эффективная выборка меньше
номинальных 222 на руку. Стандартные ошибки ниже моих, реальная мощность ещё ниже.

### Что из этого следует

Корректная формулировка замера: **«запрет агентских unit/integration-тестов не
навредил заметно и сэкономил 6% времени и 9% денег»**.

Некорректная: **«тесты доказано бесполезны»**. Это absence of evidence,
поданная как evidence of absence: тест на неполноценность (non-inferiority) не
проводился, граница эквивалентности не предрегистрирована.

**Воспроизводимости нет:** в его 77 репозиториях нет ни одного с данными этого
прогона (искала), в Substack поста нет, `pier` — от Datacurve, не от него.
«Hard empirical evidence» из твита пока не проверить ничем, кроме моей
пересчётной арифметики.

Экономию $304 → $278 проверить не могу: их тест значимости не опубликован.

## 4. Расхождения пересказа с оригиналом — три места

Пересказ (Telegram, «AI Projects», 09.10.2026) расходится с твитом:

**1. «Доказал бесполезность и даже вред TDD»**
В твите нет ни «доказал», ни «вред». Цифры показывают 65.3% → 66.2%, то есть
**выше** без тестов, и сам автор помечает «non stat-sig». Это не вред — это
**польза не обнаружена**.

**2. «Рабочими являются E2E» — приписано Kun'у**
Он писал ровно обратное по форме: «this analysis does not prove nor disprove the
value of e2e tests — i will do another eval specifically for that». Основание:
17 E2E против 3 000+ unit/integration — выборки под E2E просто нет.
Приписанный вывод про E2E — позиция автора пересказа, а не Kun.

**3. «Kun Chen заявил о доказательствах»**
Понижение регистра по сути: сам он написал «empirically proven» — риторически
это сильнее, чем выдерживает его выборка (см. раздел 3).

Также в пересказе: **«Log Driven Development» и метод GRACE — это конструкция
автора пересказа**, не Kun. У автора свой интерес (продвижение обучения).
Принцип «тесты полезны как заполнители телеметрии» сам по себе здрав, но
доказательством его замер не является.

### Отдельно: reward hacking — это другой механизм

Пересказ: «модели обучились мошенничать с тестами через reward hacking».
У Kun в твите **другой** механизм: не подгонка под известный тест, а
**общая интерпретация** — тест и код написаны из одной модели задачи, поэтому
тест не независим. Смешивать нельзя:

- от **reward hacking** спасает скрытый/внешний тест (тот, что агент не видел)
- от **общей интерпретации** не спасает ничего внутри пары «агент + агент»

### Что за E2E и LDD в этом пересказе

**E2E (end-to-end, сквозной тест)** — прогоняет весь путь сценария через
**само приложение**: от входа до результата. Не «функция вернула 42», а «открыл
форму → ввёл → отправил → ответ пришёл → запись в базе».

Почему в агентском контуре он ведёт себя иначе unit'а: истина приходит **извне
кода**. Приложение либо выполнило сценарий, либо нет — подтвердить силой
интерпретации нельзя, проверяется поведение системы целиком. Отсюда формулировка
пересказа «замена кожаного тестировщика сквозным проходом»: агент проходит
сценарий через Playwright/CLI/MCP как живой человек.

**Но сам Kun не доказал пользу E2E** — он прямо написал «does not prove nor
disprove the value of e2e tests», 17 штук против 3 000+ unit/integration,
отдельный замер обещан. Приписывать ему вывод про E2E = искажение (раздел 4).

У нас E2E уже есть правило и старше его вывода: **«End-to-end verify
(curl/browser) до отчёта»**. Реальные применения в этой сессии: сверка Superb по
живому сайту (все 8 карточек), сверка фильтра с серверным счётчиком freshauto,
GitHub API вместо DOM.

**LDD (Log Driven Development) — три разных смысла, и путаница настоящая:**

1. **Ортодоксальный** (Logz.io, 2016, DevOps): тесты НЕ отменяются — прямо
   «Develop unit and integration tests». LDD = продолжение TDD в проде:
   осмысленные логи, метрики, алерты, ответственность за код в эксплуатации.
   Тесты остаются проверкой, логи добавляются.
2. **Старый сатирический** (`log-driven-development.github.io`): «TDD/BDD/ATDD
   создают лишние проблемы» — полемическая страничка, тесты отодвигаются.
3. **В этом пересказе** — третий, авторский смысл: «тесты бесполезны как
   проверки, но полезны как **заполнители логов**: агент запускает тест, чтобы
   получить телеметрию, а выводы делает по логам».

Суть третьего: тест теряет роль проверки и становится способом **разогнать
приложение** ради логов. Проверка — логи (факты), не assert (ожидание). Это
единственное место в посте, где автор явно говорит от себя («я бы отметил»,
«в моём GRACE»).

**Цена третьего:** автоматический гейт исчезает. Упавший тест никого не
останавливает, регрессия проходит мимо — падение превращается в сигнал для
чтения лога, а не в блокер. Для регрессий старого кода это прямая потеря.

### GRACE: автор пересказа — автор GRACE, но в GRACE тесты остались

GRACE = **Graph-RAG Anchored Code Engineering**, автор **Vladimir Ivanov**
(`@turboplanner`). Канал «AI Projects» = `@turboproject`, его же VK-страница
`vk.ru/turboplanner`. То есть автор пересказа — **сам автор GRACE**: «в моём
GRACE» буквально своё, присвоения чужого нет.

Но нюанс, который стоит знать. В README самого GRACE:

- `MustPassCommand` = «leaf project evidence such as **tests**, typecheck, build»
  — тесты обязательные
- `<Command budgetSeconds="1800">bun run gate:e2e</Command>` — **E2E-гейт** в
  конфиге
- `grace-fix` — «Debug issues from graph, contracts, **tests**, traces»
- `grace-plan` — «verification gates from an approved spec»

То есть **в самом GRACE тесты и E2E-гейты остались**, а «log-driven
verification» — один из слоёв поверх. Формулировка из пересказа «TDD — опасная
химера» **сильнее того, что написано в его же проекте**: там методология живёт
со спекой, контрактами, верификационными гейтами и тестами как evidence — это
ближе к SDD с обязательными проверками, чем к «бросай тесты, читай логи».

## 5. Главный тезис Kun — верен, и он не статистический

> «both the implementation and the tests were simply the agent's interpretation
> of our intent. the tests aren't any more accurate than the implementation itself»

Это структурное свойство, а не гипотеза. **Подтверждено на нашем материале:**

1. **freshauto, 04.10.2026** — я написала фильтр по `complectation_name` и
   получила **4 машины из 10 417** вместо 144. Тест, написанный мной же тогда,
   прошёл бы: assert я написала бы из своей же неверной модели. Поймала не
   тест, а **серверный счётчик сайта** — внешняя независимая истина.
2. **«Машин нет» при живых 144** — ошибка интерпретации (дельта vs базовый
   набор), поймана Романом, не тестами.
3. **142 против 144 в отчёте** — вскрылось только сверкой с выдачей сайта.

### Граница TDD: что Iron Law гарантирует, а что нет

В нашем скилле `code-quality-workflow` — **Iron Law**: «NO PRODUCTION CODE
WITHOUT A FAILING TEST FIRST» и «если не видел, как тест падает, — не знаешь,
что он проверяет».

- **RED-шаг защищает от пустого теста** (тест, который всегда зелёный) ✅
- RED-шаг **не защищает** от того, о чём Kun: тест и код могут честно пройти
  red→green на **неправильном** понимании задачи ❌

То есть Iron Law **не опровергнут, но уже́, чем его подают**: он гарантирует,
что тест исполняется и привязан к поведению; он не гарантирует, что поведение
то самое.

### Ключ к независимости — приход истины снаружи

Единственный рабочий контур: **тест/проверка, чья истина не рождается в той же
сессии**. Варианты:

- скрытые тесты (как в DeepSWE) — агент не видит проверку
- человек-написанный или человек-авторизованный тест (сам Kun: «they express
  intent better than requirements or the implementation»)
- внешний источник данных: серверный счётчик, живой сайт, реальный прогон
- **E2E через CLI/MCP/Playwright** — бьёт по приложению целиком, правда
  приходит извне кода

Отсюда: E2E здесь — не «тест» в смысле TDD, а **замена ручного прогона**.

> У Романа это уже правило: **«End-to-end verify (curl/browser) до отчёта»**
> (USER.md). Оно старше вывода Kun и совпадает с ним по сути.

### SDD

Кun различает тестирование и TDD и формулирует позицию ближе к SDD, чем к
«логам» из пересказа: **ценность тестов появляется, когда интент приходит от
человека**. Плюс его репозиторий `vision` (VISION.md из истории репо) и тезис
про «requirements, tests, and review are the new bottlenecks».

Связь с `[[tech/sdd-deep-guide]]`: там строка **«TDD и SDD дополняют:
SDD генерирует тесты, TDD их исполняет»**. Замер Kun — контраргумент к этой
строке: генерация тестов из спеки **агентом** даёт те же две копии одной
интерпретации, если спеку тоже писал агент. Работает, только если спека — от
человека.

**Оговорка: SDD не защищает автоматически.** Работает не сам факт спеки, а
факт, что человек её **прочитал и понял**. Разница с TDD в том, что спеку
можно прочитать и сказать «нет, ты не понял» — тест прочитать так нельзя:
сотни зелёных assert'ов не сообщают, верное ли требование зашито. Поэтому у
Романа правило Plan-first (план 3+ шагов → «угу» → выполнять) — это и есть
человеческий авторитет спеки, ровно та независимость, которой не хватает
агентскому TDD. Работает, пока «угу» — реальное прочтение, а не ритуал.

Уже существующие у Романа правила, закрывающие этот пробел:
**«End-to-end verify (curl/browser) до отчёта»** (внешний контур, независимый
от того, кто что написал) и **Rule 1q** в `task-execution` (сверка чисел с
внешним источником). На неверно прочитанной спеке SDD упадёт так же, как TDD —
поэтому правило 1q и есть страховка от этого случая.

## 7. Что и где нам доработать

### Приоритет 1 — правки в скиллах ✅ ВЫПОЛНЕНО 09.10.2026

**`software-development/code-quality-workflow`** — 3 патча, 205 → 247 строк:

- Новый раздел **«Boundary of the Iron Law (read before trusting a green test)»**
  сразу после Iron Law: RED защищает от *пустого* теста, но не от *общей
  неверной интерпретации*. Три правила: называть внешний источник сверки;
  при его отсутствии — говорить прямо; тесты того же агента в той же сессии
  независимой проверкой не считаются. Внутри — наш кейс с freshauto
  (4 из 10 417) и признание, что RED покупает реальную ценность (пустые
  тесты, регрессии на чужом коде) — граница сужает утверждение, не отменяет TDD
- **Verification Checklist** получил пункт: ожидаемое поведение сверено с
  внешним источником, и источник назван в отчёте
- **Section B**: принцип «No agent should verify its own work» расширен на
  Section A — «own work» = пара «код + его тесты», а не только дифф; второй
  ревьюер получает **спеку от человека**, а не пересказ задачи от исполнителя

**`software-development/task-execution`** — новая **Rule 1q** (772 строки):

- «Сверка вывода с внешним источником перед сдачей — зелёные тесты своего же
  агента не считаются». Три инцидента freshauto как происхождение, четыре
  пункта правила: называть внешний источник форматом «сверено с X: N»;
  при отсутствии — прямо писать; вшил источник числа в отчёт-монитор;
  одинаковые числа в двух местах — сверка программой
- Где не нужно: быстрые read-only вопросы, работа, где единственный источник —
  сам файл
- Связь расписана с 1n (происхождение числа), 1g (зависимые чеки), 1h
  (первоисточник до первой версии) и с «Boundary of the Iron Law» — тот же
  тезис, но здесь как always-правило для любой сдачи

**`productivity/html-report-delivery` / отчёты-мониторы** — источник числа
вшивать в текст прогона. **Не правил**: в наших мониторах (freshauto) базовая
строка уже показывает серверный счётчик («под фильтром сейчас: N»), правило
покрыто фактически. Для новых мониторов — из текста Rule 1q.

### Приоритет 2 — проверить, не посажен ли тот же баг глубже ✅ ПРОВЕРЕНО И ИСПРАВЛЕНО 09.10.2026

**`mlops/llm-output-verification`** (Best-of-N верификатор) — **проверен,
правок не требует.** Не подпадает под механизм Kun вообще: это не «второй агент
говорит ок», а численная оценка по распределению `logprobs` (мелкозернистая
шкала 0..1, ожидание по top-k, повторы × декомпозиция критериев). Внешний
детерминированный чекер в нём уже поставлен выше LLM-оценки — в разделе
«Не подходит» прямо: «`curl`/`integrity_check`/`hermes doctor`... У пользователя
уже есть практика "сначала curl, потом браузер" — она надёжнее LLM-оценки».
Здесь же зафиксирована **наша реальная дыра**: `opencode-go` не отдаёт
`top_logprobs` → `compare` = `(0.5, 0.5)`, `select` = `[0.5,0.5,0.5]`, тихая
деградация до тай; нужны vLLM/SGLang/DeepSeek/OpenAI.

**`software-development/subagent-driven-development`** — **правка сделана** (3 патча):

- **Final Review**: во финальный integration review добавлен блок
  **`EXTERNAL CROSS-CHECK (mandatory — name the source)`** — финальный вердикт
  не может ставиться на зелёных тестах исполнителя; надо назвать внешний
  источник (живой прогон / серверный счётчик / upstream API / цитата спеки)
  форматом «cross-checked with X: <result>»; при его отсутствии — сказать
  прямо, молчание о провенансе запрещено
- **Red Flags**: два новых пункта — «назвать зелёный финал тестами одними» и
  «`git add -A`» (ломает твоё правило про репозитории с личными данными)
- **`git add -A` → явные пути** в двух местах: Step 4 (implementer-пример) и
  Verify and Commit, с комментарием про секреты/кэши/личные файлы
- Заодно отмечено: Spec Compliance Reviewer уже получает `ORIGINAL TASK SPEC`
  (спеку, а не пересказ задачи) — это верно и совпадает с правкой
  `code-quality-workflow` вчера

**`software-development/systematic-debugging`** — **правка сделана** (2 патча):

- **Phase 1 Completion Checklist**: новый пункт — воспроизведение сверено с
  **внешним наблюдением** бага (лог реального инцидента, скриншот/текст ошибки
  пользователя, поведение в проде, ответ upstream API) с указанием источника
  («matches log line X»); воспроизведение, написанное только по описанию задачи,
  может закрепить неверное понимание того, что сломано
- **Phase 4, step 1 (Create Failing Test Case)**: оговорка, что тест и фикс
  пишет один агент → тест доказывает самосогласованность, а не то, что баг
  воспроизведён верно; доверие тесту даёт только сверка Phase 1, а при её
  отсутствии это надо говорить в отчёте, а не подавать зелёный тест как
  доказательство
- Уже защищённое (правок не требовало): Phase 1 требует `Evidence gathered
  (logs, state, data flow)`, воспроизведение и трассировку данных, Iron Law
  «без расследования — никаких фиксов», корреляра про workaround

### Приоритет 3 — вещи Kun, которые можно взять ✅ В ВИКИ 09.10.2026 (без установки)

Разобраны двумя страницами, **ни одно не устанавливалось** — по правилу Романа
«новое сначала в вики, не ставить».

**`[[tools/axi]]`** — AXI (Agent eXperience Interface): 10 принципов
агентоцентричных CLI, токен-бюджет как ограничение первого класса, формат TOON
(~40% экономии против JSON). Его замеры: `gh-axi` 100% / $0.050 / 3 хода против
GitHub MCP 87% / $0.148 / 6 ходов. Оговорки зафиксированы: модель одна
(Sonnet 4.6), свои инструменты против стороннего MCP, 17 задач в бенчмарке.
Готовность VPS: Node v22.23.2, npm 10.9.8, `gh` уже установлен — `gh-axi` был бы
самым дешёвым вхождением (одна npm-команда).

**`[[tools/no-mistakes]]`** — 8 802⭐, MIT, Go, релиз v1.84.0 (26.09.2026),
последний пуш 09.10.2026. Локальный git-прокси: `git push no-mistakes` →
одноразовый worktree → пайплайн `review → test → docs → lint → push → PR → CI` →
чистый PR. Безопасные фиксы автоматом, всё, что касается интента, — эскаляция
человеку. Два найденных риска до установки:

1. `install.sh` (96 строк, прочитан) — **не проверяет `checksums.txt`**, хотя
   файл в релизе есть; криптоподписи нет вообще (для сравнения: у dcg были
   minisign + cosign). Практически: при установке вручную сверить `sha256sum`
2. **Hermes не в списке pipeline-агентов** — значатся claude, codex, grok,
   rovodev, opencode, pi, copilot, antigravity, cursor, devin, acp. Штатного
   пути для Hermes нет; возможен косвенный через `acp:<target>` / `acpx`, но это
   не проверено. Из нашего стека напрямую подходит только `opencode`

Стоит взять оттуда идею, а не бинарь: гейт в git-пути с изолированным worktree
и обязательной эскаляцией по интенту — это по сути Section B
`code-quality-workflow`, но встроенная в push. Если когда-нибудь понадобится —
`gh-axi` ставить первым (дешёвое вхождение), `no-mistakes` — вторым и только
после разбора, какому pipeline-агенту его отдать.

**`vision`** — генерация VISION.md из истории репо с стресс-тестом
гипотетиками. Кандидат для `dex-agent`: то, что у Романа решает про Декса
(личность, вкусы) — в том же направлении.

**`backpass`** — AGENTS.md не пишется руками, а «тренируется градиентным
спуском». Интригующе по звучанию (1 366⭐), требует разбора: что именно
оптимизируется.
