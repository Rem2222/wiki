# Идеи из MAPS для стека Rem

Четыре конкретные идеи из [[tech/ai-os-maps]], разобранные под то, что уже стоит на VPS и домашнем ПК. Уровень полезности — от самого большого к меньшему.

## 1. «У каждого факта ровно один дом» — правило, а не инструмент

**Суть MAPS:** ни один факт не хранится в двух местах. Если правило запрещено где-то записано — оно живёт в одном файле, остальное только ссылаются.

**Почему это про Rem прямо сейчас:** у Rem четыре независимых хранилища, и они уже конфликтуют:

| Хранилище | Что там | Риск |
|---|---|---|
| `~/Documents/wiki/` (Obsidian) | сервисы, софт, концепции, техника | основное, git + LiveSync |
| OpenViking `viking://` | профиль, предпочтения, сущности | index/extract, дублирует вики |
| Hindsight (AgentMemory) | факты/события/выводы | аномальный рост 13k+ фактов за 10 дней |
| MEMORY.md / memory tool | оперативные заметки | свой бюджет, свой формат |

Дублирование уже даёт о себе знать: тот же вопрос про провайдера приходится искать в вике **и** в памяти, а Hindsight плодит факты, которых Rem не записывал.

**Что сделать:**
- Объявить **источником истины по фактам — вики** (это у Rem уже де-факто: git, LiveSync, здравый frontmatter).
- OpenViking/Hindsight — **производные**: индексы и поиск, а не место, где факт впервые возникает.
- Правило на каждый новый факт: «куда это пойдёт?» — один ответ, остальным только wikilink.
- Раз в месяц — дедуп-проход: `zvec-wiki` по теме + сравнение с Hindsight-facts, выкидывание второго экземпляра.

**Цена:** ноль рублей, одна договорённость. **Эффект:** перестаёт спорить, где правда.

## 2. Rolling-пробки на cron-рутинах (самое дешёвое и самое защитное)

**Суть MAPS:** лимиты на рутине — **две штуки**, и обе читаются из одного лога прогонов:
1. **дневной потолок** — сколько максимум за сутки;
2. **короткое rolling-окно** (5 часов / неделя) — сколько максимум за короткий интервал.

Плюс: каждая рутина пишет строку лога «время, имя, модель, ходы, стоимость, статус», и пробки читают **этот же лог**.

**Что есть у Rem:** `/gquota` даёт видимость по Google Gemini; у Hermes cron есть 3-минутный hard-interrupt на прогон. **Нет:** единого потолка по расходу и нет rolling-окна.

**Чем это грозит сейчас:** если какая-то джоба (ночная рутина, адъютант, stall-checker) начнёт фоллбэчить или уходить в цикл — 3-минутный interrupt её останавливает на прогон, но **не мешает ей стрелять каждые N минут весь день**. Ровно так у Rem уже была история со спамом из `check-*.sh` → скилл `cron-job-forensics`.

**Что сделать (порядок работ):**
1. Добавить в cron-джобы запись одной строки в `~/.hermes/logs/cron-runs.log`: `время | job_id | модель | ходы | статус`.
2. Скрипт-проверка `cron-caps.sh`, читающий этот лог: суточный потолок (напр. 40 прогонов/сут) + rolling-окно (напр. 8 за 5 часов).
3. При превышении — `hermes cron pause <id>` + ntfy-уведомление Rem'у. Возобновление руками.
4. Обсудить с Rem пороги (это его бюджеты, не мои).

**Цена:** пара часов + 50 строк скрипта. **Эффект:** сбоющая рутина не может сжечь месячную квоту за ночь.

## 3. Ночной обход карты → `brain.json` (визуализация вики)

**Суть MAPS:** один JSON, который ночной скрипт пишет, обходя карту: каждый файл — узел, каждый wikilink — ребро. Страница рисует **один и тот же файл** шестью видами: rings / circle / areas / links / timeline / 3d orbit.

**Что есть у Rem:**
- Вики с `[[wikilinks]]` — уже граф, готовые `source → target` пары.
- zvec-индекс, где у чанков есть `page` / `category` / `title` — готовые атрибуты узла.
- Ночной скрипт — уже есть (ночная рутина Multica, шаг 5.5).
- Инструменты визуализации: скилл `markdown-viewer` (диаграммы, визуализации), `mermaid`, есть `visual-design`.

**Что нужно добавить:** один скрипт `wiki-graph.py`: идёт по `~/Documents/wiki/**/*.md`, парсит frontmatter (category/title/updated) и wikilinks, пишет `data/brain.json` по схеме выше (kind/layer — вывести из категории и типа файла). Кладёт в то место, откуда тянет дашборд.

**Ключевое правило MAPS, которое важно не нарушить:** дашборд **только читает** свой `data/`. Ночная рутина пишет, страница — никогда. Тогда дашборд можно спокойно снести и пересобрать, ничего не теряется.

**Почему стоит делать:** Rem уже смотрит в вику руками и через `zvec-wiki`. Граф даёт то, чего не даёт поиск: **видимость связей и протухания** (timeline по `updated` сразу покажет мёртвые области).

**Цена:** один скрипт + одна страница. **Эффект:** вики становится видимой, а не только искабельной.

## 4. Синк вики git-ом между VPS и домашним ПК

**Суть MAPS:** одна папка живёт на двух машинах, синк сам через git каждые 5 минут в обе стороны; на сервере — сеть закрыта (Tailscale) и профиль, которому запрещено отправлять/шарить/удалять.

**Что есть у Rem:** вики — git-репозиторий (`Rem2222/wiki`), Obsidian Git plugin тянет её на телефон и домашний ПК. То есть **синк уже есть**.

**Чего нет:** на домашнем ПК тот же агентский доступ к вике (Hermes Desktop есть, но вики-скиллы и zvec — на VPS). И Rem сейчас — «человеческий роутер» между агентами, которые не умеют общаться напрямую.

**Что реально можно взять из Card 2:**
- **Профиль-ограничение** — не «запрети всё», а «может написать, не может отправить». У Rem это `approvals.mode` + `website_blocklist` + отсутствие messaging-инструментов в отдельных профилях. Стоит оформить как **отдельный профиль Hermes для машины, которая работает без присмотра**, чтобы ограничение было свойством профиля, а не доброй волей.
- **Не открывать порты ради удобства** — у Rem наоборот стоит задача «вынести сервисы наружу, чтобы не гонять Tailscale». Здесь MAPS против: закрытое по умолчанию + явные исключения.

**Цена:** оформление профиля. **Эффект:** меньше соблазна дать безнадзорной машине messaging-инструменты.

## Что НЕ стоит брать

- **Card 0 (интервью) и signpost-карта с нулевого места** — у Rem карта уже есть и она лучше: wiki + index.md + frontmatter + health-check. Строить signpost-и с нуля = сломать работающее.
- **Собственный дашборд на stdlib** — у Rem уже Beszel + Grafana + Prometheus. Своё = ещё один мертвый проект.
- **Замеры «−40% токенов» как гарантию** — это самозамеры автора на его workspace. На wiki+zvec у Rem другой профиль запросов.
- **Claude Code setup-token flow** — Rem не на подписке Anthropic как основной стек.
