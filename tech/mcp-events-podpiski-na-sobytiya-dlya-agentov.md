# MCP Events — подписки на события для агентов

## Суть

MCP Events — расширение `io.modelcontextprotocol/events`, которое позволяет MCP-клиенту подписываться на события upstream-систем и передавать их агенту, даже когда пользователь ничего не спрашивает. Пример из поста: новый pull request в GitHub → агент сам запускает проверку кода и тесты. Записано 21.11.2026 в 18:21 МСК по живой проверке репозитория, SEP и спецификации. Статус для нас: не подключалось, наблюдаем.

## Статус проекта

- Репозиторий `modelcontextprotocol/ext-events` — официальный инкубатор Tasks and Events Working Group, Apache-2.0, создан 09.04.2026, последний пуш 20.11.2026.
- На момент проверки: 63 звезды, 12 форков, 17 открытых issue, 5 подписчиков. README прямо помечает это как Experimental: это не официальная спецификация рекомендаций.
- SEP-3415 (Events Extension, автор Питер Александер) имеет статус Final с 05.10.2026. Сама спецификация расширения — Beta. Это разные вещи: дизайн принят, но ломающие изменения возможны и будут документироваться.
- Работает только с MCP revision 2026-07-28 и новее: нужны `server/discover`, `subscriptions/listen` и extension negotiation.
- Руководители рабочей группы — Клэр Лигуори и Лука Чанг из AWS, Катрин Маккафри из Microsoft, Питер Александер.

## Что именно показано на схеме и что упущено

- Последовательность верная: `events/list` → типы событий с `name`, `inputSchema`, `payloadSchema`, `delivery` → `events/poll {name, arguments, cursor: null}` → `{events: [], cursor, nextPollMs}` → ожидание → `events/poll` с курсором → `{events: [occurrence], cursor, nextPollMs}` → передача события в agent runtime.
- Схема упрощает ответ: в спецификацииpoll-результат дополнительно содержит `truncated` и `hasMore`. При `hasMore: true` клиент должен опрашивать сразу, не выжидая `nextPollMs`.
- Три режима доставки называются точнее, чем в посте: Poll — `events/poll`, Push — `events/stream`, долгоживущий запрос с доставкой событий в потоке ответа; Webhook — `events/subscribe`, HTTPS-колбэк с подписью и TTL, который клиент обязан обновлять. Все три объявляются на уровне типа события, ни один не обязателен.
- Курсор непрозрачен для клиента. `null` в запросе означает «начать с сейчас». Если сервер не может продолжить с сохранённой позиции, он возвращает `truncated: true`, и клиент знает, что события пропущены.
- Клиент владеет каноническим списком подписок. Для poll серверу не нужно хранить состояние — это делает протокол пригодным для serverless и клиентов за NAT.

## Зачем это вообще

- Обычные MCP-уведомления не несут аргументов и полезной нагрузки, требуют открытого соединения и не имеют курсора. После разрыва клиент не знает, что пропустил.
- Events добавляет фильтры подписки, схему данных и честную сигнализацию о пропусках. Разница принципиальная: не «что-то изменилось», а «создан P1-инцидент в таком-то сервисе с такими-то полями».
- Безопасность описана трезво: полезная нагрузка события считается недоверенной, как результат вызова инструмента; авторизация идёт через тот же principal, что и у tools.
- В репозитории уже идут field reports и споры: issue #23 — подписка есть, но агент только уведомляет; #22 и #21 — рассогласование с Standard Webhooks по проверке endpoint и коду 410; #13 — требование делать подписки только для чтения.

## Готовность реализаций

- TypeScript SDK: PR #3209 «feat: Events extension (SEP-3415)» открыт и остаётся draft по состоянию на 20.11.2026.
- Python SDK 2.3.0 также имеет примитивы регистрации расширений, но готового событийного клиента в дереве нет; есть отдельные field reports и примеры.
- Сторонние проекты подходят по кусочкам: fast-agent — draft PR с poll-доставкой, punkpeye/mcp-proxy — экспериментальная передача `events/poll`, frontmcp — отдельные релизы для poll, stream и subscribe.
- Вывод: описание и спецификация есть, зрелой кросс-SDK поддержки ещё нет. Это ранняя стадия, а не готовый инструмент.

## Чем интересно Роману

- Как сейчас: агенты ждут запроса в чате или запускаются кроном. Как станет: событие снаружи само разбудит агента — новый PR, письмо, инцидент, изменение в БД. Для SmithsChat это был бы ещё один источник сообщений помимо текущих long-poll и ручных вызовов.
- Как сейчас: пример «новый PR → проверка кода и тесты» в Hermes уже решается собственными webhook subscriptions, без MCP Events. Как станет: если события стандартизуются, можно будет перейти с разовых вебхуков на общий протокол с курсором и фильтрами.
- Как сейчас: `hermes webhook list` сообщает, что webhook-платформа не включена; в MCP-клиенте Hermes нет обработки `events/*` и расширений-events. Как станет: потребуется отдельный код или поддержка в Hermes, а не просто подключение сервера.
- Чего НЕ делает: не заменяет крон, не даёт самой проверки кода, не решает вопрос прав доступа. Для 1С прямого применения нет.

## Статус на 21.11.2026

Записано, НЕ подключалось. Никакие конфиги и пакеты не менялись. Webhook-платформа Hermes остаётся выключенной, MCP-серверы не добавлялись. События MCP не работают в текущем стеке «из коробки».

## За чем наблюдать

- Переход расширения из Beta в стабильное состояние и прекращение ломающих изменений.
- Появление готовой поддержки Events в официальных Python- и TypeScript-SDK, а не в draft PR.
- Разрешение разногласий со Standard Webhooks и по семантике 410 Gone.
- Появление реальных серверов с `events/list` для GitHub, почты и мониторинга — без них протокол остаётся интересной бумажкой.
- Возможность.actionable-событий для агента, а не только уведомлений «что-то случилось».
