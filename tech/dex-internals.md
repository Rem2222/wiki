# Dex — внутреннее устройство

Разобрано по исходникам 30.09.2026. Коммит `6e89dd3`.
Страница обновлена **вечером 30.09** — тогда же появились инструменты, скилы, задачи и команды.

## TL;DR

**Dex — агент с ограничениями.** У него есть tool-calling с песочницей, скилы,
задачи и память. Он работает от **root**, поэтому доступ жёстко ограничен:
только чтение, только 6 каталогов, секреты закрыты.

**Три независимых Python-процесса** лежат рядом с Hermes, дёргают один LLM
одним HTTP-запросом и общаются между собой через файлы и SQLite.
Четвёртый файл — `dex_tools.py` — общая библиотека инструментов.

| Файл | Строк | Роль |
|---|---|---|
| `dex_poller.py` | 946 | Telegram ↔ LLM, команды, цикл инструментов |
| `heartbeat.py` | 974 | тик каждые 10 мин, исполнители, задачи, драйвы |
| `dex_tools.py` | 1060 | песочница, схемы `tools`, шаблоны команд, fetch, диспетчер |
| `dex_control.py` | 381 | веб-панель и API на `127.0.0.1:3333` |

## Три процесса

| Процесс | Как запускается | Роль |
|---|---|---|
| `dex-poller` (systemd --user) | `dex_poller.py`, цикл с паузой **3 с** | Telegram ↔ LLM. Offset в `.poller_offset` |
| `dex-control` (systemd --user) | `dex_control.py`, Flask | Дашборд на `127.0.0.1:3333`, наружу `rem2222.top/dex/` (nginx + Authelia). Свой venv (flask 3.1.3) |
| `dex-heartbeat` (cron) | `heartbeat.py`, каждые **10 мин**, `no-agent` | Тик: решение одним словом → `execute_*()` → тик в журнал |

Красная кнопка `DISABLED` общая для всех трёх.

## Два разных «мозга»

Под именем «Dex» живут **две разные системы**.

### Общение (poller)

```
identity.yaml      → system prompt (+ состояние + инструменты + индекс скилов)
sessions.db        → последние 30 сообщений (15 обменов)
+ твоё сообщение   → LLM-запрос с блоком "tools"
                        │
                        ├─ вернулся текст        → ответ в Telegram
                        └─ вернулись tool_calls  → ЦИКЛ (до 4 шагов)
                                                    выполняем → дописываем → переспрашиваем
```

Один запрос — это теперь не предел: `chat_with_tools()` гоняет до 4 раундов.
На лимите делает последний запрос **без** `tools`, чтобы получить связный ответ.

### Сердцебиение (heartbeat)

```
состояние (тик, фокус, драйвы, долги, последние 3 тика, открытые задачи)
→ LLM отвечает ОДНИМ СЛОВОМ из белого списка
→ if/elif исполняет готовую функцию
```

Белый список: `check_updates, check_backups, check_disk, check_tools,
check_services, explore_interest, none`. Всё прочее отбрасывается как `bogus`.

## Луп: 7 шагов

```
1. Флаг DISABLED?        → спим (флаг с until= снимается сам по истечении)
2. tick_count += 1, токен, identity, БД
3. Контекст: последние 3 тика, фокус, драйвы, просроченные duties,
   открытые задачи
4. Сборка промпта
5. call_llm(max_tokens=20) — ответ одним словом
6. Валидация по белому списку
7. execute_*() → maybe_file_task() → запись тика → отчёт в Telegram
```

Интервалы обязанностей: диск и сервисы — **час**, бэкапы / обновления /
инструменты — **сутки**. Просроченное подставляется в промпт строкой
«Пора проверить: …», но решение всё равно за LLM.

## Инструменты и песочница

**12 схем** отправляются провайдеру блоком `tools` — но видит модель **10 на уровне 3** и все 12 на уровнях 1–2 (см. «Уровни доступа» ниже):

| Инструмент | Что делает |
|---|---|
| `read_state` | тик, фокус, драйвы, последние тики |
| `run_check` | 6 чеков: `disk, backups, updates, services, tools, interest` |
| `read_file` | первые строки файла (лимит 200) |
| `list_dir` | содержимое каталога |
| `tail_log` | последние строки журнала |
| `list_skills` | индекс процедур |
| `read_skill` | текст процедуры целиком |
| `tasks` | `list` / `add` / `done` — свои задачи |
| `run_cmd` | **14 именованных шаблонов** вместо произвольной строки: `journalctl-unit`, `journalctl-since`, `systemctl-status`, `systemctl-user-status`, `docker-logs`, `docker-inspect`, `git-log`, `git-status`, `net-ports`, `memory`, `load`, `top-by-mem`, `disk-inodes`, `docker-stats` |
| `fetch_url` | читает публичную страницу и отдаёт **текст**; SSRF-защита |
| `write_file` | запись файла — **только уровни 1–2** |
| `run_script` | запуск своего `.py` — **только уровни 1–2** |

**Песочница (`dex_tools.py`)** — обязательна, Dex работает от root:

```
ALLOWED_ROOTS:  /root/.hermes/proactive   /root/.hermes/scripts
                /root/backups             /var/log
                /etc                      /root/Documents/wiki/ops/services
DENY:  .env  auth.json  shadow  gshadow  sudoers  ssh  ключи  token  password
Лимит: только чтение, обрезка результата 4000 символов, «..» запрещён,
       имя скила — только буквы/дефисы
```

Проверено на живых отказах: `/etc/shadow`, `/root/.hermes/.env`, `/tmp/x`,
`../etc/passwd` — все закрыты.

### Шаблоны команд (вариант А)

Произвольной строки у модели нет. `run_cmd(template, args)` берёт один из
**14 заранее описанных `argv`**, каждый слот проходит regex, значение с
ведущим `-` отклоняется (защита от подмены флага), запуск — списком,
`shell=False`, с таймаутом и обрезкой результата.

```
14/14 попыток инъекции отклонены:
  dex-poller; rm -rf /   --help        0;cat /etc/shadow
  ../../etc              $(whoami)     отсутствующий шаблон
```

Закрытые дыры: слот-путь режется на `DENY_SUBSTRINGS` (раньше
`git-log /root/.hermes/.env` проходил), имена systemd-юнитов из вики
валидируются regex **до** попадания в `argv systemctl` (в `_registry_units`
и повторно в `_unit_states`), а `systemctl --user` получает
`XDG_RUNTIME_DIR` явно — без него было «Failed to connect to bus:
No medium found» и молча пустой результат.

### Чтение сайтов: `fetch_url`

Отвечает на потребность драйва любопытства: доступен **на всех уровнях**
(это тоже чтение), лимиты 15 с / 400 КБ, редиректы обрабатываем сами —
до 5 штук, **каждый шаг проверяется заново**, иначе ушёл бы на приватный
адрес.

SSRF-защита:
- только `http`/`https`, `localhost` и metadata-хосты заблокированы списком
- литерал IP проверяется на публичность
- **все адреса из DNS** проверяются тоже — `localtest.me → 127.0.0.1`
  отсекается, как и `169.254.169.254` (метаданные облака) и 10/8, 172.16/12,
  192.168/16, `::1`
- HTML превращается в чистый текст (выкидываем `script`/`style`/`svg`)

Тесты: `example.com` 0,1 с, GitHub API 0,3 с, Wikipedia 0,5 с,
12/12 SSRF-попыток отклонены.

### Уровни доступа 3 / 2 / 1

Хранятся в `agent.db` (`state.access_level`), **по умолчанию 3**.
`active_tools()` фильтрует схемы, поэтому модель на уровне 3 **не видит**
`write_file`/`run_script` вообще — не «отказ в рантайме», а отсутствие в
запросе.

| Уровень | Что даёт | Ограничения |
|---|---|---|
| **3** — только чтение | 10 схем | записи и запуска нет |
| **2** — песочница | + `write_file` в `sandbox/` и `skills/`, + `run_script` | от **nobody (65534)**, **сеть отрезана** (`unshare --net`), лимиты CPU 20 с / память 1 ГБ / файл 10 МБ / дескрипторы 64 |
| **1** — root | + запись по `/root/.hermes`, + запуск от root | сеть есть, артефакты остаются |

**Проход через `/root` (0700) у nobody невозможен**, поэтому на уровне 2
скрипт и входные файлы копируются в одноразовый каталог 0777 в `/tmp`,
а созданные файлы **забираются обратно в `sandbox`**; `tmp` удаляется.

Входные файлы (`inputs`) берутся только из read-allowlist и копируются
в `_in`, чтобы их читал уже `nobody`.

Переключение в Telegram:
```
/access        показать        — без подтверждения
/access 2      снизить        — нужен /yes
/access 1      до root        — нужен /yes
/access 3      вернуться       — сразу, направление безопасное
```
Также `GET /api/status` → `access_level`.

### Почему цикл понадобился

Провайдер `gemini-web2api` возвращает нормальные `tool_calls` (проверено ещё
30.09 утром), но в коде не было «выполнил → дописал → переспросил» — поэтому
Dex честно отвечал «у меня нет доступа к файлам».

## Скилы

Каталог `~/.hermes/proactive/skills/<имя>/SKILL.md` с YAML-фронтматтером
(`name`, `description`, `when`) и телом из шагов.

```
service-diagnostics   как диагностировать упавший сервис и что отчитывать
disk-pressure         как найти виновника нехватки места, ничего не удаляя
what-changed          кто и что изменил на сервере, с разделением фактов и гипотез
```

Короткий индекс («имя — назначение») вставляется в system prompt, **полный текст
Dex читает сам** через `read_skill` — так промпт не раздувается.

**Живой тест:** «упал сервис, что делать?» → сам вызвал
`read_skill(service-diagnostics)` → ответил шагами из скила (37 с, 1 вызов).

## Задачи

Таблица `tasks(id, what, status, source, result, created_at, done_at)` была
создана ещё в июле, но **никем не использовалась** (0 строк).

Теперь задачи — это список дел, которые Dex заметил, но сам **не может** сделать:
песочница разрешает только чтение, лечить может только Ром.

- `task_add` — с **дедупликацией** по тексту
- `maybe_file_task()` — автосоздание из чеков:
  `check_services` нашёл неактивные → задача; диск ≥ 90% → задача;
  «нет файлов бэкапов» → задача
- открытые задачи попадают в промпт тика, а старше суток — **копят драйв
  `diligence`** (потребность не насыщена)
- инструмент `tasks` + команды `/tasks`, `/task`, `/done`

> **Ловушка с дедупликацией.** Первый вариант клал в `what` список неактивных
> юнитов — а он меняется от тика к тику, и одна проблема породила задачи #2 и #7.
> Решение: в `what` только **стабильная фраза** («разобраться с неактивными
> сервисами»), детали в `result`. Проверено на двух разных списках → одна задача.

## Драйвы (модель v2, внедрена 30.09)

| Событие | Эффект |
|---|---|
| простой тик (`none`) | `curiosity +0.10` |
| просроченная обязанность | `diligence +0.05` |
| задача старше суток | `diligence +0.05` |
| выполнена обязанность | `diligence −0.30` |
| `explore_interest` | `curiosity −0.40` |
| другое действие | `curiosity −0.10` |
| границы | пол `0.10`, потолок `1.00` |

Модель утверждена Романом 30.09: **потребность копится, пока не выполнена,
и сбрасывается действием**.

> **Почему понадобилась правка.** Изначальная логика была перевёрнута: драйв
> увеличивался **после** выполненного действия и **нигде не убывал**. За 1371 тик
> оба упёрлись в `1.0` и стали константой — то есть делал он что угодно,
> а «сильно хотел» всегда.
>
> Разовый сброс `migrate_drives()` (маркер `drives_v2`) перевёл `1.0/1.0 → 0.4/0.4`.

Голые числа LLM игнорирует, поэтому при `≥ 0.7` в промпт добавляется прямая
подсказка («выбери explore_interest» / «выбери обязанность»).

## Команды Telegram

Раньше были `/start` и `/status`, остальное отвечало «команда пока не
реализована». Теперь:

```
Состояние      /status /state · /last · /drives · /memory <запрос>
Проверки       /check <name> · /skills · /skill <имя>
Задачи         /tasks · /task <текст> · /done <id>
Управление     /tick · /pause [мин] · /resume · /restart
/access [1|2|3] · /help
```

**Белый список — обязательно, в двух местах.** `ALLOWED_CHAT_IDS = {386235337}`
проверяется и в `process_message`, и в `handle_command`. Первого оказалось мало:
`handle_command` можно позвать напрямую, минуя вызывающую функцию — точка входа
тоже должна проверять. Чужой `chat_id` получает «Это личный бот» и лог.

**Подтверждение — обязательно.** `/pause`, `/restart`, `/tick` сначала сохраняют
ожидающую команду в `state` и просят `/yes`; `/no` отменяет. TTL — **120 секунд**,
устаревшее подтверждение сбрасывается.

**`/restart` имеет смысл** — не из-за промпта (он собирается заново на каждое
сообщение), а из-за `sessions.db`: там лежат последние 30 реплик и подгружаются
в каждый запрос. Очищает **только строки своего `chat_id`**.

**`/pause N` снимается сам.** В флаг `DISABLED` пишется `until=<ISO>`;
heartbeat проверяет его перед сном. Флаг без `until` ведёт себя как раньше —
вечно, пока `/resume`.

## Уведомления и дайджест

С 30.09 в Telegram уходит **каждое действие** (обещание «отписываться на каждый тик»),
а не только аномалии. Кулдаун на идентичный текст держит поток в **~14–15 сообщений/сутки**
(не 49 — одинаковые результаты глушатся).

| Действие | Кулдаун |
|---|---|
| `check_disk`, `check_backups`, `check_services` | 6 часов |
| `check_updates`, `check_tools` | 24 часа |

Аномалии (`≤10G` свободно, «нет файлов», `inactive`/`failed`) идут приоритетным форматом.
Дайджест — сводка раз в сутки, до 12 записей, с дедупликацией.

## Память: четыре хранилища

| Хранилище | Содержимое |
|---|---|
| `identity.yaml` (2.6 КБ) | Личность: имя, роль, 9 черт, 8 интересов, 5 обязанностей. Основа system prompt |
| `agent.db` (WAL) | `state` (счётчики, фокус, драйвы, кулдауны, дайджест, `pending_cmd`), `llm_log` (~1400), `tasks` (рабочая), `config`, `ticks_meta`, `vec_ticks` |
| `sessions.db` (77 КБ) | Диалоги: `chat_id, role, content, ts`. В промпт — последние **30** |
| `tick_history.jsonl` | Append-only журнал тиков: номер, действие, результат, время. Сейчас **1404** |

### Векторная память (sqlite-vec + bge-m3)

`vec0.so` (159 КБ, из wheel `sqlite_vec 0.1.9`, **без** `pip install` — тот упирается
в PEP 668) лежит в `~/.hermes/proactive/lib/` и подключается через
`connection.load_extension()`.

- таблица `vec_ticks` — `vec0(embedding float[1024])`, `rowid` = номер тика
- эмбеддинги — `bge-m3` через Ollama `:11434/api/embed`, 1024 измерения
- сборка — `vec_build.py`, **уже инкрементальная**: добавляет только тики,
  которых нет в `ticks_meta`. Догон 6 тиков — 5,5 с (полная сборка 1362 → 4,3 мин)

**Ключевой приём: дедупликация.** 1362 тика давали всего **~69 уникальных** строк
`action: result` (857 тиков `none` = 4 текста). Эмбеддим каждую строку один раз
и раздаём вектор всем тикам с этим текстом — **4,3 минуты вместо ~2 часов**.

### Как поиск подключён к чату

`dex_poller.search_memory(query)` — KNN-поиск, возвращает до 4 похожих тиков.

- **Свежесть вместо древних дублей.** `vec0` запрещает второй ключ в
  `ORDER BY` (`Only a single 'ORDER BY distance' clause is allowed`), а
  дубликаты текста дают одинаковое расстояние — поэтому без обработки
  побеждал бы **самый старый** тик. Решение: тянем пул из 30 кандидатов и
  сортируем сами по `(distance, -tick)`.
- **Ворота `wants_memory()`.** Эмбеддинг запроса стоит **1–7 секунд**
  (зависит от загрузки Ollama), поэтому на обычные вопросы и на вопросы
  о текущем состоянии поиск пропускается — там ответ уже есть в блоке
  состояния. Проверено 7/7 тестовых запросов.
- **Блок помечен как ИСТОРИЯ** — иначе устаревшие цифры выдаются за
  текущие (так и случилось на первом тесте: назвал 21G, когда уже было 27G).

Результат:

```
В: Были ли у тебя проблемы с бэкапами?
О: «Да, бывало. В начале августа (тики #1016, #1020, #1022, #1027)
    висели ошибки: бэкапы вообще не находились.
    Сейчас по свежему тику всё норм»
```

Раньше такой ответ был невозможен — в промпт не попадала ни одна история тиков.

> **Почему не сразу `pip install sqlite-vec`.** Системный Python под PEP 668
> (`externally-managed-environment`). Решение — достать `vec0.so` из wheel
> и подключать по пути. Не трогает системное окружение.

## Две ошибки, допущенные и найденные 30.09

Обе — мои, в этой же сессии. Записаны, чтобы не наступать снова.

1. **Потерянный `Bearer`.** При переписывании `call_hermes()` в заголовок
   попала строка `Authorization: *** ` — она скопирована из вывода `read_file`,
   а тот **редактирует `Bearer <ключ>` в `***`**. Провайдер отвечал
   `invalid api key`, и виновник выглядел как «ключ протух».
   Сверка с `git show HEAD:dex_poller.py` показала, что `Bearer` там был.
   **Правило: секреты и заголовки не копировать из вывода инструментов.**

2. **`systemctl` без `--user`.** `check_services` врал «inactive» для
   работающих сервисов. **Правило: юниты `dex-*` живут в менеджере сеанса.**

## Диагностика 30.09 (утро): откуда брались странные ответы

Разобрано три отдельных причины, **не** связанных с размером контекста
(промпт всего ~800 токенов, у модели контекст огромный):

1. **Провайдерная ошибка Google.** Воспроизведено чистым запросом без истории:
   просьба «открой файлы, найди правила» → сервер Google отвечает
   *«Я не могу использовать Workspace, потому что необходимые параметры Gmail
   отключены»*. В `sessions.db` таких ответов 5. Теперь: ловим → повтор → честный ответ.
2. **Конфабуляция про sqlite_vec.** Dex утверждал, что прикрутил векторную
   память. Проверено: в БД не было ни одной виртуальной таблицы, расширение
   не установлено, в коде ноль упоминаний. Фраза лежала **в его собственном
   system prompt** — `identity.yaml:32` и `README.md:53` (этап 5, статус 🔜).
   Он пересказывал план как свершившийся факт. **Вечером 30.09 это стало правдой.**
3. **Отсутствие ground truth.** В диалоге были только `identity.yaml` + 10 реплик,
   поэтому каждый ответ он достраивал заново и **противоречил предыдущему**.
