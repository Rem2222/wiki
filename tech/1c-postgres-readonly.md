# PostgreSQL 1С: доступ агенту только на чтение

Практическая схема для случая «ИИ-агент должен напрямую строить запросы к базе 1С, которая живёт в PostgreSQL». Написано под конкретный риск: агент с правами записи в базу 1С ломает учёт, потому что обходит платформу.

## Почему только чтение

База 1С в PostgreSQL — это не прикладная схема с осмысленными именами, а генерируемое платформой хранилище: таблицы `_ReferenceNN`, `_DocumentNN`, поля `_FldNNNN`, ссылки в двоичном виде в `_IDRRef`. Регистры, версии объектов, итоги, блокировки и вся бизнес-логика живут в платформе. Прямой `INSERT`/`UPDATE` меняет «сырое» состояние в обход этой логики: объект останется без движений по регистрам, версии разъедутся, восстановить корректность постфактум почти невозможно.

Вывод: агенту — только `SELECT`. Запись — исключительно через платформу (обработки, обмены, API 1С).

## Роль в PostgreSQL

```sql
CREATE ROLE ai_readonly LOGIN PASSWORD '<пароль>';
GRANT CONNECT ON DATABASE <база> TO ai_readonly;
GRANT USAGE ON SCHEMA public TO ai_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO ai_readonly;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO ai_readonly;
```

Дополнительно закрыть доступ к служебному:

```sql
REVOKE CREATE ON SCHEMA public FROM ai_readonly;
REVOKE ALL ON DATABASE <база> FROM PUBLIC;
```

Запрет записи на уровне сессии — важнее, чем права на таблицы, потому что он срабатывает даже если гранты случайно расширят:

```sql
ALTER ROLE ai_readonly SET default_transaction_read_only = on;
ALTER ROLE ai_readonly SET statement_timeout = '30s';
ALTER ROLE ai_readonly SET idle_in_transaction_session_timeout = '60s';
ALTER ROLE ai_readonly SET work_mem = '64MB';
```

Проверка после настройки (обязательна):

```sql
-- от имени ai_readonly
SELECT current_setting('default_transaction_read_only');   -- ожидаем on
SELECT count(*) FROM <любая_таблица> LIMIT 1;               -- работает
INSERT INTO <любая_таблица> VALUES (...);                   -- должен упасть с ошибкой
```

Пока `INSERT` не падает — доступ не готов, и агенту его отдавать нельзя.

## Сеть

- В `postgresql.conf`: `listen_addresses` — только внутренний адрес, не `*`, если база не обязана быть доступна извне
- В `pg_hba.conf`: строка для `ai_readonly` с `scram-sha-256`, только с нужных адресов
- Снаружи базу не открывать вообще; доступ агента — через VPN/mesh (Tailscale и подобное), где видно, кто именно подключается
- Проверка со стороны агента: подключение должно работать изнутри и **не** работать с внешнего адреса

## Рабочая база или копия

Тяжёлый аналитический запрос на живой базе — это блокировки и просадка отклика у пользователей. Предпочтительный порядок:

1. **Копия базы** (`pg_dump`/`pg_restore` в отдельный инстанс, либо `pg_basebackup`). Агент работает по копии, обновление — по расписанию.
2. **Реплика** (streaming replication) — если нужна свежесть.
3. **Рабочая база** — только на чтение, с `statement_timeout`, `LIMIT` и пониманием, что нагрузка делится с людьми.

## Что агенту нужно знать про имена

Без метаданных чтение бесполезно: `_Reference123` ничего не говорит. Поэтому SQL-доступ имеет смысл только в паре со слоем метаданных — либо MCP-серверы метаданных 1С (`1c-code-metadata-mcp`, `1c-graph-metadata-mcp`), либо собственный справочник соответствий «таблица ↔ объект метаданных ↔ реквизиты». Подробнее — в [[tech/nvidia-auto-ontology]].

Ещё два практических момента:

- Имена таблиц и полей **меняются при реструктуризации** базы, поэтому справочник соответствий нужно перегенерировать после каждого изменения конфигурации
- Ссылочные поля (`_IDRRef`) — двоичные; сравнение и соединения делаются по ним, а «человеческое» представление подтягивается из таблиц объектов

## Оговорка

Допустимые версии PostgreSQL зависят от версии платформы 1С — это сверяется по документации ИТС под конкретный релиз (у меня нет данных о текущем релизе платформы на контуре, поэтому конкретные версии здесь не называю: предположение, не проверял).
