# Harness² (Google Research) — рекурсивный харнессинг агентов без обучения весов

**Harness²** (Harness2) — фреймворк Google Research для «рекурсивного харнессинга» агентов: оптимизация обвязки вокруг модели при **неизменных весах** самой модели. Проверено 24.10.2026 по GitHub API, README и docs/SETUP.md.

- Репозиторий: https://github.com/google-research/harness2
- **18 923 ⭐**, 1 838 форков, создан 06.10.2026, язык Python, лицензия **Apache-2.0**
- Статья: arXiv **2610.14224** · сайт: https://harness2.github.io
- В поиске GitHub уже 104 репозитория вокруг него: плагин для DeepSeek Harness (`Xnmk029/dsh-plugin-harness2`), red-team-эксперимент (`kenhuangus/harness2-redteam`), конфигурации сообщества

**Статус: не установлено, не запускалось.** Записано по факту чтения исходников; на VPS не ставилось (см. блокеры).

## Идея

«Harness» — вся система вокруг модели, которая превращает её в агента: промпты, инструменты, память, скиллы, оркестрация. «Harnessing» — оптимизация этой системы. Harness² делает это в два уровня рекурсии:

- **Task-level recursion** — на текущей задаче выполняется контрастный цикл **Propose–Probe–Compose**: предложить правки harness → зондировать их влияние на той же задаче → собрать уточнённый harness из **поведенческих контрастов** между прогонами. Принципиально: **без ground-truth**, то есть без правильных ответов, только по различиям в поведении.
- **Harnessing-level recursion** — принятые улучшения и «уроки с доказательствами» копятся в постоянном *improvement harness*, который направляет следующие задачи.

## Заявленные результаты (не проверялись нами)

Один шаг Harness² на трёх профессиональных бенчмарках и четырёх конфигурациях «модель–harness»:

- **+11.5** пунктов на WorkBuddy-Bench
- **+11.8 п.п.** по partial pass rate на LAB
- **+4.5** пункта на JobBench
- Модели: GLM-5 и Gemini 3.5 Flash. Увеличение бюджета task-level рекурсии (`--k`) даёт дальнейший рост.

Формулировка «та же модель делает работу на 10+ пунктов лучше» верна для двух бенчмарков из трёх; на JobBench прирост вдвое скромнее. Сами авторы пишут «gains of up to».

## Что поддерживается

- Режимы рекурсии: `--mode parallel` и `--mode sequential`, бюджет `--k`
- Executors: **OpenCode** (по умолчанию) и **Codex** (`--substrate cx`)
- Бенчмарки: **JobBench** (данные с HF `JobBench/job-bench`), **LAB** (upstream `harveyai/harvey-labs`, юридические задачи с рубриками), **WorkBuddy-Bench**
- Команды: `harness2-setup <bench>` → `harness2-check` → `harness2 --bench …` → `harness2-judge` → `harness2-report`

## Требования (docs/SETUP.md)

- Linux, **Python 3.12**, `uv`, **Node.js 20+**, Docker Engine (для WorkBuddy-Bench, нужен рабочий `docker info`)
- `pandoc` и `poppler-utils` — для LAB
- **Google Cloud CLI + Vertex AI**: исполнители и судья по умолчанию идут через Vertex Gemini; нужен GCP-проект и `gcloud auth application-default login`
- Переменные: `HARNESS2_SOLVER_MODEL` (формат OpenCode `provider/model`), `HARNESS2_IMPROVER_MODEL`, `HARNESS2_JUDGE_MODEL`, `HARNESS2_RUNS_DIR`
- Смена модели судьи меняет измерение: сравнимые прогоны требуют одинаковых run/judge/report параметров

## Что из этого применимо у нас

Ценность не в бенчмарках, а в приёме: **улучшать обвязку агента без разметки**, сравнивая поведение двух прогонов. Это прямо ложится на **Dex** (`Rem2222/dex-agent`) — у него есть свои скиллы, промпты и инструменты, но нет размеченных данных.

Перенос без Vertex, вручную:

1. Взять реальную задачу и прогнать дважды — с правкой harness (промпт/скилл/инструмент) и без.
2. Сравнить поведенческий контраст: где именно разошлись шаги, вызовы инструментов, длина, ошибки.
3. Принять правку только при подтверждённом контрасте; иначе откатить.
4. Копить принятые правки и уроки в отдельном файле — это и есть «improvement harness» в миниатюре.

Такой цикл согласуется с принятой моделью развития Dex: read-only → песочница → патчи на ревью → автоприменение со сторожем (3 неудачных тика → откат + сигнал).

## Вывод

Сильная и уже заметная работа про то, что «модель — не всё»: обвязка оптимизируется отдельно и без весов, без разметки, прямо на рабочей задаче. Для нас практический интерес — метод Propose–Probe–Compose, а не запуск их стенда: стенд требует Vertex AI и места на диске.
