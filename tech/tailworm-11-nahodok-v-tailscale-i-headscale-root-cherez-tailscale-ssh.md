# Tailworm: 11 находок в Tailscale и headscale (root через Tailscale SSH)

**Tailworm** — публичный аудит-отчёт по Tailscale и headscale: 11 находок, включая повышение привилегий до root через встроенный Tailscale SSH. Проверено 24.10.2026 по первоисточнику (tailworm.com), наша экспозиция — живой проверкой на VPS.

- Автор: **Erica Windisch**, Cyberdione Labs · опубликовано **24–25.10.2026** (страница отчёта — 24.10 17:38 GMT, обсуждение на HN — 25.10)
- Тестирование: **22–24.10.2026**, на **немодифицированном** ПО — tailscale **v1.104.2** и headscale **v0.29.5**, все находки воспроизведены в лаборатории
- Идентификаторы находок: **T1–T3, C1–C4, F-1–F-5** (11 штук, 5 групп)
- **CVE нет, фикса нет, Tailscale находки не подтвердила.** Раскрытие не координированное: исследователь считает, что инфраструктура уязвима уже сегодня, и опубликовала сразу. Связи с Tailscale Inc. и оплаты за работу нет (заявлено в отчёте)

## Пять классов находок

1. **Tailscale SSH** (встроенный SSH-сервер внутри `tailscaled`, процесс работает как **root**). Unix-socket forwarding (`ssh -L` / `ssh -R`) выполняет проверки путей и файловые операции **от имени root**; гонки TOCTOU обходят статический allowlist `{home, /tmp, /run/user}`. Демонстрация из отчёта: проброс на `docker.sock` → `docker run -v /:/host` → **`uid=0(root)` и содержимое `/etc/shadow`** за 0 секунд, без sudo и без членства в группе docker. Через `ssh -R` (BindUnlink) можно подменить root-сокет и получить исполнение кода в демонах с command-channel, а также перехватить креды container registry.
2. **App connectors (`conn25`, экспериментальный)** — коннектор транслирует трафик на выбранный атакующим адрес **без валидации**, сетевые ACL не учитываются для настоящего адресата. Итог: доступ к cloud metadata (креды серверов) и ко всем внутренним сервисам Kubernetes.
3. **headscale** (self-hosted control server) — неаутентифицированное исчерпание ресурсов: рост памяти, вытеснение кэша → crash loop и блокировка подключения новых устройств. Дополнительно: **в 0.29.5 forwarding отключить нельзя**, он выдаётся безусловно на каждой принятой сессии — то есть каждый SSH-грант в headscale эквивалентен root.
4. **DERP relay client** — при подключении к враждебному релею агент можно истощить.
5. **`tailscale serve`** — TCP-forward на unix-socket без защиты, которая есть на HTTP-пути, плюс гонка в авторизации per-mount → удалённое открытие admin-API.

## Почему это серьёзно (wormability)

Измерено в лаборатории: связка «Tailscale SSH разрешён политикой» + находки класса 1 даёт **автоматическое распространение** по всем устройствам, которые разрешены политикой — без паролей, без украденных ключей, без участия пользователя, **меньше секунды на один хоп**. Украденные ключи ноды позволяют атакующему подключить свою машину как «легитимный tagged server» с авто-одобренными маршрутами.

Остановили распространение только две вещи: **per-pair grants** (точечные разрешения на пару устройств — единственный контроль, который сработал) и **аппаратная привязка ключей** (TPM/Secure Enclave). Все прочие меры влияли лишь на скорость обнаружения, а не на распространение.

## Митигации по убыванию эффекта (из отчёта)

1. **Per-pair SSH grants** — никогда не давать разрешения «на всю identity» или «на весь тег».
2. **Отключить SSH forwarding**: в SaaS — выставить per-rule forwarding в false; в headscale 0.29.5 нельзя, поэтому считать любой SSH-грант root-эквивалентным. Ограничение SSH непривилегированными аккаунтами **не помогает** — находки работают из полностью непривилегированных аккаунтов.
3. **Node-key expiry** для серверного парка + состояние агента в TPM/Secure Enclave.
4. Телеметрия безопасности — вне досягаемости скомпрометированного сервера.
5. Ограничить entitlements коннекторов, allowlist адресатов, default-deny egress в namespace коннектора.
6. Реагирование строить на **удалении устройства в control plane**: ключи ноды лежат в файле, root их скопирует, и переустановка хоста уже не отзывает украденную копию — отзывает только удаление в control plane или истечение ключа.
7. Для self-hosted control plane: лимиты памяти, супервизия рестартов, троттлинг регистрации.

## Наша экспозиция — проверено 24.10.2026

- **Tailscale SSH выключен**: `RunSSH = False`. Находки класса 1 (повышение до root) к нам **не применимы**.
- **serve/funnel не настроены**: `tailscale serve status` → «No serve config». Класс 5 закрыт.
- **headscale не используем** (SaaS-tailnet `rem2222@gmail.com`), **app connectors / conn25 не используем** → классы 2 и 3 не применимы.
- **DERP**: класс 4 теоретический — нужен враждебный релей.
- **SSH**: свой `sshd` на **22022**, ufw разрешает только из `100.64.0.0/10` (то есть лишь по Tailscale). Наружу не открыт.
- **Версия 1.102.2** — старее тестируемой 1.104.2, то есть потенциально подвержена тем же багам. Главный риск снят тем, что Tailscale SSH выключен; при выходе фикса — обновиться.

**Отдельно, не про Tailworm, но обнаружено при этой проверке:** в ufw есть правило «Anywhere ALLOW IN 100.80.140.66» (домашний ПК XE2690 — полный доступ) и **открытый наружу порт 2586** (ntfy). Это стоит пересмотреть отдельно.

## Вывод

Отчёт сильный по существу и слабый по процедуре: находки воспроизведены и это не теория, но раскрытие не координировано, подтверждения от вендора и CVE нет. Ключевая претензия автора — не отдельный баг, а **дизайн**: отказ от эшелонированной защиты, замена OpenSSH с разделением привилегий на один привилегированный процесс, и границы сети шире, чем обещано.

Практический вывод для нас: пока Tailscale SSH и serve выключены, основные классы риска не работают. Если когда-нибудь понадобится Tailscale SSH — только per-pair grants, без forwarding, с аппаратной привязкой ключей.
