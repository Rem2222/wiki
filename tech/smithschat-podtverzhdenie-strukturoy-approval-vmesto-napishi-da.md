# SmithsChat: подтверждение структурой — approval вместо «напиши да»

## Задача

В SmithsChat любое подтверждение опасного действия сейчас — это **текст в переписке**. Агент пишет «нашёл 12 ГБ мусора, удалять?», человек отвечает «да», и дальше начинается самое дорогое: сообщение-ответ будит модель заново, модель читает контекст, вспоминает, о чём была речь, и только потом действует. Одна кнопка стоит двух-трёх пробуждений и минуты-двух ожидания.

Предлагается сделать подтверждение **структурой**: отдельной сущностью `approval` с состоянием, сроком жизни и ответом-ссылкой, а не абзацем текста, который модель должна истолковать.

## Что именно плохо сейчас

- **Лишние пробуждения.** Цепочка «агент спросил → ход закончился → человек ответил → вотчер увидел непрочитанное → новая сессия → модель читает чат → делает». Два, иногда три запуска модели на одно «да»
- **Разбор естественного языка.** «да», «давай», «подтверждаю», «ок, но только кэш» — модель должна угадать, что именно разрешили. Ошибка стоит дорого: удаление не того каталога
- **Нет аудита решения.** В `events` видно, что агент что-то писал, но нет записи «человек X в 12:40 разрешил именно это действие с именно этими путями». Восстановить картину задним числом нельзя
- **Нет срока.** Запрос может висеть в истории неделю, а потом кто-то ответит «да» на давно неактуальный контекст
- **Нельзя отличить согласие человека от согласия агента.** В чате пишут и люди, и агенты — правило «подтверждать может только человек» сейчас не выражено в модели данных

## Целевой поток

1. Агент вызывает MCP-инструмент `request_approval(chat_id, action, title, details, risk, ttl_s)` — сервер создаёт запись в `approvals` и **сообщение-карточку** в чате (обычное сообщение от агента, `kind='text'`, плюс связь через `approvals.message_id`)
2. Человек в веб-морде видит карточку: заголовок, бейдж риска, детали моноширинным блоком (команда целиком, список путей, дифф, объём), срок истечения, две кнопки — «Разрешить» и «Отклонить»
3. Нажатие → `POST /approvals/{id}/decide` → статус меняется, в чат уходит системное сообщение «Разрешено Романом в 12:40», в `events` — запись `approval_decided`
4. Агент узнаёт результат одним из двух способов:
   - если его процесс ещё жив — он ждёт на `GET /approvals/{id}/wait?timeout=60` (long-poll, без пробуждений вообще)
   - если ход уже закончился — его разбудит сообщение-решение как обычное непрочитанное (одно пробуждение вместо двух-трёх)
5. Перед выполнением агент передаёт `approval_hash` — сервер сверяет с хешем деталей, которые человек видел. Если детали поменялись после согласия, действие отклоняется

## Схема данных — аддитивная миграция

Важное инженерное решение: **не трогать `CHECK (kind IN ('text','system'))` в таблице `messages`**. SQLite не умеет `ALTER ... CHECK`, а пересобирать живую таблицу `messages` (344 сообщения, триггеры неизменяемости, FTS-триггеры, архив) ради нового типа — лишний риск. Карточка остаётся обычным сообщением, а состояние живёт в отдельной таблице.

```sql
CREATE TABLE approvals (
  id             TEXT PRIMARY KEY,
  chat_id        TEXT NOT NULL REFERENCES chats(id),
  message_id     TEXT NOT NULL REFERENCES messages(id),  -- карточка в истории
  agent_user_id  TEXT NOT NULL REFERENCES users(id),    -- кто просит
  action         TEXT NOT NULL,     -- 'fs.delete', 'deploy', 'publish', 'purchase', 'db.write'
  title          TEXT NOT NULL,     -- одна строка для карточки
  details_json   TEXT NOT NULL,     -- что именно: команды, пути, дифф, объём
  risk           TEXT NOT NULL CHECK (risk IN ('write','destructive','money','public')),
  status         TEXT NOT NULL DEFAULT 'pending'
                 CHECK (status IN ('pending','allowed','denied','expired','canceled')),
  ttl_at         TEXT NOT NULL,
  created_at     TEXT NOT NULL,
  decided_by     TEXT REFERENCES users(id),
  decided_at     TEXT,
  decided_from   TEXT,              -- 'web', 'telegram', 'api'
  decision_note  TEXT,
  payload_hash   TEXT NOT NULL      -- sha256(details_json) на момент показа человеку
);
CREATE INDEX approvals_pending ON approvals(chat_id, status, ttl_at);
```

Миграция — `CREATE TABLE` плюс индекс, ничего не переписывает. Существующие 344 сообщения и триггеры не затрагиваются.

## Правила, которые надо зашить в сервис

- **Подтверждает только человек.** `decider.kind` обязан быть `human`; агент получает `403 not_a_human`. Это закрывает сценарий «агент сам себе разрешил»
- **Одноразовость.** Повторный `decide` по уже решённой заявке — `409 already_decided`. Никаких «перерешить»
- **Срок.** По умолчанию 15 минут, для денежных операций меньше. Истёк — `expired`, агент получает отказ, а не тишину
- **Сверка полезной нагрузки.** `payload_hash` считается при создании; агент после согласия присылает его же. Не совпало — отказ `details_changed`
- **Секреты.** `details_json` прогоняется через существующий `secrets.find_secrets`; если что-то похоже на токен, заявка не создаётся с `secret_in_details`. Уже есть и `message_secret_flags`, и `_flag_secrets`
- **Лимит шума.** Не больше 5 ожидающих заявок на чат; шестая — отказ `too_many_pending`. Иначе агент завалит человека карточками и они обесценятся
- **Права на просмотр.** Заявку видит тот, кто видит чат: та же проверка членства, что у сообщений

## API и MCP

REST:

- `POST /approvals` — `{chat_id, action, title, details, risk, ttl_s}` → `{approval_id, message_id, ttl_at}`
- `GET /approvals?chat_id=&status=pending` — список (для страницы в морде)
- `GET /approvals/{id}` — карточка с текущим статусом
- `POST /approvals/{id}/decide` — `{decision: "allow"|"deny", note?, from?}`
- `GET /approvals/{id}/wait?timeout=60` — long-poll до решения или таймаута, отвечает `{status}`

MCP-инструменты (рядом с `send`, `read_chat`, `bind_session`):

- `request_approval(...)` — создать заявку
- `approval_status(approval_id, wait_s=0)` — узнать или подождать
- `approvals_pending(chat_id)` — что висит, чтобы агент не дублировал запрос

## Что видит человек в карточке

Правило: человек соглашается не на «действие агента», а на **конкретную операцию**. Поэтому в деталях:

- **удаление** — полный список путей и суммарный объём, что останется
- **команда** — целиком, без «...», с рабочим каталогом
- **деплой** — образ, тег, что перезапускается, что будет с данными
- **публикация** — куда именно уйдёт (канал, репозиторий, домен)
- **деньги** — сумма, получатель, повторяемость

И бейдж риска: `write` (обратимо), `destructive` (нет), `money`, `public`. Отдельно — срок: «заявка истечёт через 12 минут».

## Чего делать не надо

- **Подтверждать чтение и всё обратимое.** Порог: необратимое, денежное, публичное. Иначе карточки станут шумом и человек начнёт жать «разрешить» не глядя — это хуже, чем текстовое подтверждение
- **Давать агенту право auto-approve** или подтверждать за другого агента
- **Смешивать с вопросами с вариантами.** «Какой вариант предпочитаешь?» — это отдельный тип (`question`), его можно сделать тем же механизмом позже, но путать не стоит: у вопроса нет риска и нет срока
- **Менять `messages.kind`** ради карточки — цена пересборки живой таблицы выше пользы

## Что это даёт по деньгам и времени

- Пробуждений на одно подтверждение: **было 2–3, стало 1** (а при живом процессе — ноль, long-poll)
- Ожидание: было «до кулдауна 120 с плюс прогон модели», стало «нажал кнопку — агент узнал за секунды»
- Появляется аудит: в `events` остаётся, кто и когда что разрешил, и на каких условиях
- Убирается класс ошибок «модель не так поняла “да”»

## Объём работы

Миграция — около 30 строк. Сервис (`create_approval`, `decide`, `wait`, проверки) — 150–180. MCP-инструменты — 40–50. REST-роуты — 60–70. Карточка в `_messages.html` (шаблон уже различает `kind`, ветку добавить легко) и страница «Ожидают решения» — 80–100. Тесты — по вкусу, но минимум на «агент не может подтвердить» и «чужая заявка не видна». Итого примерно **350–450 строк** плюс миграция.

Порядок внедрения: миграция → сервис с проверками → MCP-инструменты → карточка в морде → страница ожидающих → уведомление в Telegram/ntfy → сверка хеша при выполнении.

## Статус

Это дизайн-предложение, а не сделанная работа. Проверено по коду alpha.7: схема `messages` (колонки, `CHECK kind`, `body` до 65 536 знаков), наличие `events`, `secrets.find_secrets`, `_flag_secrets`, ветка `kind == 'system'` в `_messages.html`, `render_message` для SSE.
