# Виджеты Telegram: HTML прямо в сообщении (widget-sandbox)

## Что это

Официальный репозиторий Telegram (`TelegramMessenger/widget-sandbox`) — фреймворк **виджетов**: один самодостаточный HTML-документ, который едет прямо в сообщении и рисуется в клиенте как интерактивный блок. Не ссылка, не файл, не мини-приложение — новое медиа сообщения.

Заявленная мотивация в документации прямая и про нас: «кроме Markdown, AI-агенты присылают в ответах HTML-виджеты — графики, калькуляторы, квизы, формы», и типовой сценарий «бот зовёт Claude API, получает HTML, кладёт его в сообщение, клиент показывает». Corpus примеров в репозитории сгенерирован сессией Claude Code, в корне лежат `.claude/` и `CLAUDE.md`.

Цифры на 10.11.2026: **163 звезды**, 6 форков, создан 12.10.2026, последний пуш в день проверки, язык HTML, версия в `VERSION.json` — **0.6.3** (protocol 1, profile 1, sdk 1). Файла LICENSE в корне нет, GitHub API лицензию не определяет — для чужого кода это надо держать в голове.

## Как устроено

Виджет — это `messageMediaWidget` с полями `width`, `height` и `payload` (новый тип медиа в API layer 233). payload — HTML, сжатый **zlib (RFC 1950, не gzip)**: сервер жмёт девятым уровнем сам и принимает только если **после сжатия ≤ 4096 байт**, а распакованный HTML — **≤ 32768 байт**. Служебные данные (`chat_data`, `public_data`, ответ бота) — по 1024 байта.

Жизненный цикл: бот отправляет виджет → клиент рендерит его в песочнице → человек тапает внутри → виджет может спросить бота (тот обязан ответить за 15 секунд) → бот правит **состояние** виджета, не пересоздавая сообщение. HTML после отправки неизменяем, меняются только данные — это «фиксированный код плюс изменяемое состояние».

Исполнение — не браузер: **QuickJS на отдельном потоке**, вместо DOM — шим, а `fetch`, `XMLHttpRequest`, `WebSocket` и `EventSource` заглушены, то есть сети у виджета нет. Входящий HTML проходит валидатор по allowlist: элементы, атрибуты, CSS-свойства; URL разрешены только `data:` для картинок и `#fragment`. Есть квоты: процессорное время в секунду, 64 МБ памяти, 256 таймеров, пауза когда виджет вне экрана.

Клиенты: web (Shadow DOM), iOS и macOS (Swift, форк QuickJS, WKWebView), Android (Gradle, NDK и WebView), desktop (C++ для tdesktop). Включается флагом раскатки; на клиентах ниже layer 233 виджет приходит как «неподдерживаемое медиа» с подписью.

## Проверено живьём на нашем боте (10.11.2026)

Метод **уже работает в обычном Bot API, не только в бете** — это главное, что выяснилось практикой. `sendWidget` ответил `ok: true` и отправил виджет в личку (message_id 29159). Бета-эндпоинт `api.telegram.org/beta/bot<token>/test/…` нашим ключом отдаёт 401, а продакшен-метод доступен.

Что ещё подтвердилось опытом:

- `width`, `height`, `is_shared`, `public_data` — принимаются без ошибок
- HTML около 6 КБ **несжимаемого** текста → отказ `INPUT_MEDIA_WIDGET_TOO_LARGE`; HTML 40 КБ → тот же отказ. То есть лимит жёсткий и считается по сжатому размеру
- `editMessageWidgetData` по отправленному виджету → `ok: true`, состояние меняется без нового сообщения
- `deleteMessage` по виджет-сообщению работает как с обычным сообщением
- обычные методы Bot API на виджет-сообщении не падают: `editMessageReplyMarkup` отвечает «message is not modified», то есть сообщение живое и редактируемое
- **`message_thread_id` обязателен в форуме**: без него виджет прилетает в тему General, и человек его не видит. С указанием темы приходит `is_topic_message: true` и нужный `message_thread_id`; `editMessageWidgetData` тоже его принимает

Отдельно: отобразился ли виджет на конкретном клиенте — вопрос к клиенту. Если Telegram старый, вместо карточки будет «неподдерживаемое медиа» с подписью.

## Что виджет умеет и чего не умеет

Умеет (SDK v1): брать тему клиента и профиль, реагировать на тапы, открывать ссылки (`openLink`, `openTelegramLink`), отдавать тактильный отклик, хранить состояние в Web Storage на своё сообщение, спрашивать бота и получать ответ.

Не умеет: ходить в сеть, читать файлы, показывать ввод с клавиатуры (в v1 нет), сам инициировать сообщение в чат (только запрос к боту), отправляться в каналы напрямую — только форвардом, пересылаться через `copyMessage` (запрещено), существовать на клиентах ниже layer 233.

Ограничения частоты: не больше 5 запросов за 5 секунд на пару «пользователь + бот», правки состояния под общим флуд-контролем `sendMessage`, один edit объекта в секунду.

## Что говорят открытые issues

- **#2 «Критически маленькие лимиты HTMLBubble после zlib»** (07.11.2026, русскоязычный автор) — главная практическая боль: 4096 байт после сжатия почти целиком съедают картинки в base64. У него HTML с CSS занял 1117 байт, и на две WebP-картинки осталось ~3 КБ — влезают только 163×109 пикселей. Вывод: **рисовать надо кодом (CSS/SVG), а не картинками**
- **#1** — виджет не форвардится
- **#3** — на iOS один процесс WebKit для общего окружения (по желанию)
- **#4** — на desktop дробные числа в `publicData`/`chatData` обрезаются до целых
- **#5** — тексты ошибок беты расходятся с документацией

## Чем интересно Роману

Сейчас → станет:

1. **Статус сервера.** Сейчас приходит простынёй текста (uptime, свободная память, диск) или ссылкой на `rem2222.top`. С виджетом — компактная карточка в чате: три строки, полоска заполнения диска, кнопка «обновить», которая спрашивает бота и обновляет цифры в том же сообщении.
2. **Отчёты.** Сейчас большой разбор уходит ссылкой на HTML-страницу. Виджет этого не заменит (32 КБ), но над ссылкой может стоять сводка с переключателем разделов — а полный текст остаётся по ссылке.
3. **Сравнение моделей и тарифов.** Сейчас списком в тексте. С виджетом — переключаемые колонки, где видно цену и лимиты без простыни.
4. **Подтверждение действия.** Кнопка внутри виджета отправляет боту запрос, бот отвечает — то есть «нажми, чтобы применить» можно делать карточкой, а не отдельным сообщением с reply-кнопками.

Ради чего это вообще: Telegram фактически узаконил то, что агенты и так делают — присылают HTML вместо текста. Только теперь он рисуется в чате, без перехода по ссылке и без стороннего хостинга.

## Статус

Разобрано и **проверено живьём на нашем боте 10.11.2026**: `sendWidget` доступен в обычном Bot API, отправка, правка состояния и удаление работают, лимит по сжатому размеру подтверждён отказом. В Hermes ничего не встраивалось, плагинов не ставилось. Непроверенным осталось главное бытовое: как виджет выглядит и работает на клиенте Романа — это видно только на его экране.
